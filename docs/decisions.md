# Архитектурные решения (ADR)

> Каждое решение по инструментам и архитектуре фиксируется здесь. «Нативное проверено» означает живую проверку реестра коннекторов, а не память.

## ADR-001 — Движок системы: субагенты Claude Code, standalone, game-lead = корень
Система game-dev — самостоятельная (не вложена в другие системы агентов). Движок — субагенты Claude Code (`.claude/agents/*.md`). `game-lead` запускается как главная сессия (`claude --agent game-lead`) и порождает специалистов.
**Причина:** субагент Claude Code не может порождать субагентов (подтверждено по code.claude.com/docs). Делая `game-lead` корнем-главной-сессией, получаем рабочее дерево «лид → специалисты». Будь game-lead вложенным субагентом, он не смог бы звать специалистов. Запас на многоуровневость в будущем — через agent teams (отдельный механизм), не через субагенты.

## ADR-002 — modeler-3d: Blender через официальный сервер blender-mcp (CLI-уровень)
Инструмент 3D — официальный сервер **blender-mcp v1.0.0** (Blender Lab), заведённый в Claude Code **CLI**, НЕ через бандл Claude Desktop.
- Установка: `uv tool install` из `git+https://projects.blender.org/lab/blender_mcp.git#subdirectory=mcp`. Бинарь: `C:\Users\pgr40\.local\bin\blender-mcp.exe`.
- Регистрация: проектно в `.mcp.json` (сервер `blender`).
- Привязка к агенту `modeler-3d` через `mcpServers: [blender]` (только этот агент видит инструменты Blender).
- Сторона Blender: аддон **Blender Lab v1.0.0**, слушает `localhost:9876`, auto-start.
Самодельный MCP на `bpy` не используем — есть официальный сервер.
**Статус:** заведено и проверено живыми вызовами (get_objects_summary, get_object_detail_summary, render_viewport_to_path). Рабочие нюансы — см. [ADR-011](#adr-011--blender-рабочие-нюансы-один-клиент-на-сокет-output_path-у-render_viewport).

## ADR-003 — unreal-operator: MCP-сервер @runreal/unreal-mcp (UE Python/Remote Execution под капотом)
Нативного коннектора Unreal в реестре Claude нет (проверено несколькими запросами — граница проверки), встроенного навыка тоже нет → по правилу «нативное первым» спускаемся на уровень MCP. Выбран сервер **`@runreal/unreal-mcp`**, который ходит в редактор по UE Python / Remote Execution. Computer Use остаётся крайним случаем, если программного пути не хватит.
- Регистрация: проектно в `.mcp.json`, сервер `unreal`. **Запуск через абсолютный путь к `node.exe` + абсолютный путь к `dist/bin.js` пакета** (`command: "C:\\Program Files\\nodejs\\node.exe"`, `args: ["…\\@runreal\\unreal-mcp\\dist\\bin.js"]`) — надёжная форма, по аналогии с blender (полный путь к бинарю).
  - **Почему не голый `npx`:** 2026-06-06 первая попытка упала на старте — `claude mcp list` показал `unreal … ✗ Failed to connect`, тулы `mcp__unreal__*` в сессию не загрузились. Причина: неинтерактивная оболочка, через которую харнесс стартует MCP-серверы, **не видит `C:\Program Files\nodejs` в PATH** (`npx`/`node` NOT FOUND), хотя Node реально установлен (node v24.16.0). blender-сервер цепляется, т.к. задан полным путём к `.exe`. Фикс — указать **абсолютный путь к `node.exe`** и прямо к `dist/bin.js` пакета, минуя резолв `npx`.
- **Multicast Bind Address = `0.0.0.0` обязателен** (UE → Project Settings → Plugins → Python Remote Execution). С дефолтным loopback-адресом multicast от node-клиента **не сходится** с редактором, тулы не отвечают. На Windows ставить именно `0.0.0.0`.
- **Редактор UE должен быть открыт и ПОЛНОСТЬЮ загружен ДО старта `claude`.** Если проект ещё грузится / редактор не поднят — MCP-сервер `unreal` стартует и сразу падает (`exit → ✗ Failed to connect`), тулы в сессию не попадают. Порядок: сначала открыть проект в UE и дождаться полной загрузки, затем запускать `claude`.
- Привязка к агенту: `unreal-operator` через `mcpServers: [unreal]` (только он видит `mcp__unreal__*`, по правилу из CLAUDE.md).
- Сторона UE: проект открыт в редакторе, **Python Editor Script Plugin** + **Enable Remote Execution** включены; к редактору подключается один клиент.
- **Предусловие рантайма:** серверу нужен **Node.js**. 2026-06-06 установлен `winget install OpenJS.NodeJS.LTS` → **node v24.16.0**, npm 11.13.0 (`C:\Program Files\nodejs`). Пакет `@runreal/unreal-mcp` существует (`npm view` → version 0.1.4).
**Статус: ПРОВАЛИДИРОВАН живыми вызовами** (2026-06-06, смоук-тест в сессии). Поднялось **20 тулзов `mcp__unreal__*`**. `editor_project_info` → проект **ContrarySurvivor**, движок **UE 5.5.4** (`5.5.4-40574608+++UE5+Release-5.5`), **GAS + Enhanced Input** включены, 7233 ассета. Запись/чтение/удаление проверены: create+delete `SmokeTestCube` (outliner 5→6→5), `HighResShot` дал реальный PNG (визуально подтверждён Ринатом).
- **Рабочие квирки (проверено живыми вызовами):**
  - **Скриншоты:** рабочий рецепт постоянного снимка — **окно UE в фокусе** → `editor_console_command HighResShot <WxH>` → файл в `<ProjectDir>/Saved/Screenshots/WindowsEditor/`. Без фокуса high-res пайплайн **не тикает** и не завершается (`is_task_done()` висит). `editor_take_screenshot` рендерит корректно, но пишет в **эфемерный tmp** (harness удаляет до след. вызова) — для отдаваемых артефактов непригоден. SceneCapture2D из Python даёт **неосвещённый/чёрный** кадр — не использовать для скринов сцены.
  - **`get_unreal_project_path()` в обёртке возвращает «not set»** → путь брать из `editor_project_info` / `unreal.Paths` (либо разово выставить `set_unreal_project_path`). Реальный путь проекта: `E:/ContrarySurvior/ContrarySurvivor/`.
  - **`editor_get_world_outliner` отдаёт внутренние имена актёров, не labels** → для точечных операций резолвить label через Python либо удалять/искать по label (`editor_delete_object` по label работает).

## ADR-004 — concept-artist: визуальный инструмент + сужение скоупа роли (ПЕРЕСМОТРЕН)
Нативного коннектора-генератора изображений в реестре Claude нет. Инструмент роли `concept-artist` — **нативный code-render**: визуал строится кодом (`HTML/CSS` + инлайн `SVG`) и рендерится в `PNG/PDF` через **headless Microsoft Edge (Chromium)**; письменная арт-дирекшн — в `.md`. Внешние AI-генераторы изображений не вводим.

**Сужение скоупа роли (2026-06-08, решение Рината — закрытие роли, Хвост 1).** Скоуп `concept-artist` сужен до того, что нативный тулсет закрывает с реальной практической пользой:
- **В скоупе:** (1) палитры / цвето- и типосистемы (HTML/SVG → PNG/PDF); (2) UI-макеты (HUD, меню) на HTML/CSS — сильная сторона роли; (3) письменная арт-дирекшн в `.md` (настроение, референс-разбор, обоснование палитры); (4) текстовые спек-листы на ассет для `modeler-3d` (ключевые формы, пропорции, размеры, лимит полигонов, референсы).
- **Убрано из скоупа:** силуэты/блокауты форм и градиент-мудборды — на практике пользы не давали. Не делать, не имитировать.
- **Честная граница (нативно не закрывается):** фигуративный/живописный концепт-арт (детальный рисунок персонажа/сцены «от руки») требует генератора изображений, которого в тулсете нет → `concept-artist` эскалирует `game-lead`, не имитирует code-render'ом.

**Генерацию изображений и Claude Design рассмотрели и НЕ вводим (2026-06-08):**
- **Нативная генерация картинок Claude — нет.** Claude не генерирует изображения нативно; коннектора-генератора в реестре Claude нет (граница проверки — реестр коннекторов). Поэтому фигуративный арт остаётся вне тулсета (см. границу выше).
- **Claude Design (он же «canvas»/web-инструмент дизайна) — не подключается к Claude Code как тул.** Это отдельный продукт/поверхность, не коннектор и не навык, доступный из Claude Code; подключить его как инструмент роли нельзя. Не вводим.
- **Внешние AI-генераторы изображений — против native-first и духа ADR-004.** Сторонние генераторы (вне нативного коннектора/навыка) нарушают правило «нативное первым» из CLAUDE.md и предыдущее решение ADR-004 (внешние генераторы не вводим). Не вводим.
- Итог: фигуративный концепт-арт сейчас закрытого нативного пути не имеет — это осознанная граница роли, а не временная заглушка.

**История решения (исходное допущение про canvas-design не подтвердилось):**
- **(a)** Первая редакция ADR-004 предполагала «нативный навык canvas-design (png/pdf)» со статусом «проводка на Фазе инструментов». Живая валидация (Ш7, 2026-06-08) показала: навык **не был установлен и недоступен** — ни как preload, ни on-demand. Проверено тремя независимыми наблюдениями со стороны `concept-artist` (teammate) + подтверждено `game-lead` (главная сессия): в system-reminder реестре навыков `canvas-design` отсутствует у обоих; прямой `Skill(canvas-design)` → `Unknown skill`; ФС-скан `.claude/skills/**` пуст. Это **не** баг прокидывания в teammate (#29441) — навыка не было в установке вообще.
- **(b)** По содержанию (сверено по `anthropics/skills`, решение Рината 2026-06-08) `canvas-design` — навык **абстрактного искусства / постеров**, а НЕ под функциональный скоуп роли (палитры, мудборды, силуэты/блокауты, UI-макеты, арт-дирекшн). Поэтому основным инструментом роли его не делаем, даже будучи установленным.
- **(c)** Решение: основной инструмент — **нативный code-render через Edge headless**. Рабочая форма подтверждена живым рендером (2026-06-08): `msedge.exe --headless=new --disable-gpu --hide-scrollbars --no-sandbox --window-size=W,H --screenshot=OUT.png "file:///ABS.html"` → реальный валидный PNG. PDF — тем же Edge с `--print-to-pdf`. Toolchain машины: Edge есть; Python/Pillow НЕТ (только Store-заглушка) → палитры/силуэты идут через SVG/HTML→Edge; Node v24 есть (puppeteer/sharp — запас). Инструменту `concept-artist` добавлен `Bash` (без него нативный путь неисполним).
- **(d)** **Ограничение (нативно не закрывается):** фигуративные/живописные концепт-зарисовки (детальный рисунок персонажа/сцены «от руки») требуют генератора изображений, которого в нативном тулсете нет. Code-render технически способен и на силуэты/блокауты/мудборды, но из практического скоупа роли они исключены (см. блок «Сужение скоупа роли» выше) — актуальный скоуп: палитры/типосистемы, UI-макеты, арт-дирекшн, текстовые спек-листы. Фигуративный рисунок code-render не закрывает в принципе. Такие задачи `concept-artist` эскалирует `game-lead`, не имитирует.

**Статус: ПЕРЕСМОТРЕН — нативный code-render (Edge headless), валидирован живым рендером Ш7 (2026-06-08); скоуп роли сужен и закрыт (2026-06-08, Хвост 1).** См. также инструкцию роли `.claude/agents/concept-artist.md`.

## ADR-012 — unreal-operator: автономный скриншот без фокуса окна (take_high_res_screenshot)
Рабочий рецепт **автономного** снимка редактора UE 5.5 **без вывода окна в фокус и без кликов** — для отдаваемых артефактов. Уточняет/дополняет квирк «Скриншоты» из [ADR-003](#adr-003--unreal-operator-mcp-сервер-runrealunreal-mcp-ue-pythonremote-execution-под-капотом): рецепт с `HighResShot`+фокус остаётся валидным для ручного снимка, ниже — автономная альтернатива.

**Рецепт (проверен живыми вызовами 2026-06-07):**
1. Через `editor_run_python` вызвать `unreal.AutomationLibrary.take_high_res_screenshot(W, H, out)`, где `out` — **постоянный** путь (напр. `<ProjectSavedDir>/Screenshots/WindowsEditor/auto_shot.png`, папку создать `os.makedirs(..., exist_ok=True)`).
2. Готовность проверять **по факту записи файла**: `os.path.exists(p)` + `os.path.getsize(p)` через `editor_run_python`. Файл пишется отложенно (по завершении кадра), обычно ~3–5 с; при NOT_YET — подождать и перепроверить.
3. **НЕ использовать `editor_take_screenshot`** — рендерит в эфемерный tmp, который harness удаляет до следующего вызова (для отдаваемого артефакта непригоден).
4. **НЕ использовать `HighResShot`** для автономного режима — high-res пайплайн требует фокуса окна, без фокуса не тикает и `is_task_done()` висит.

**Обязательное предусловие (иначе файл не запишется):**
- Настройка редактора **"Use Less CPU when in Background" = OFF** (троттлинг CPU в фоне выключен).
- Окно редактора **открыто и НЕ свёрнуто** (свёрнутое/троттлящее окно не тикает кадры → `take_high_res_screenshot` ставит запрос в очередь, но PNG не пишется).

**Доказательство (протокол B):** 1-й прогон 2026-06-07 при включённом троттлинге → `NOT_YET` (файл не появился за ~6 с). После OFF + развёрнутого окна — повтор тех же шагов → `OK`, `E:/ContrarySurvior/ContrarySurvivor/Saved/Screenshots/WindowsEditor/auto_shot.png`, **1 594 187 байт** (подтверждён `os.path.getsize`).

**Ограничение: предусловие машинное, не проектное — в репо не попадает.**
- "Use Less CPU when in Background" — это ключ `bThrottleCPUWhenNotForeground` в секции `[/Script/UnrealEd.EditorPerformanceSettings]` (класс `UEditorPerformanceSettings`, модуль `UnrealEd`).
- Хранится в **per-user/машинном** файле `%LOCALAPPDATA%\UnrealEngine\5.5\Saved\Config\WindowsEditor\EditorSettings.ini` (фактически найдено: `C:\Users\pgr40\AppData\Local\UnrealEngine\5.5\Saved\Config\WindowsEditor\EditorSettings.ini`, строка `bThrottleCPUWhenNotForeground=False`).
- В конфигах **проекта** (`E:/ContrarySurvior/ContrarySurvivor/Saved/Config/**`, `.../Config/**`) ключа **нет** (рекурсивный поиск — пусто). Значит **в систему контроля версий не попадает** и на другой машине/у другого пользователя его нужно **выставлять заново вручную** (Editor Preferences → General → Performance → снять «Use Less CPU when in Background»).
- Гипотеза для переноса в репо (НЕ проверено, требует дизайн-решения): значение потенциально можно зафиксировать на уровне проекта через `Config/DefaultEditorPerProjectUserSettings.ini` с той же секцией/ключом — такого файла в репо сейчас нет. Применять только после живой проверки, что project-default перебивает per-user значение.

## ADR-013 — ContrarySurvivor: риск дрейфа AFS SecurityToken в публичном репо (ЗАКРЫТО — риск принят)
Контекст: проектные `Config/*.ini` репозитория **ContrarySurvivor** (`github.com/RenchezLove/ContrarySurvivor`, **публичный**) заведены под VCS, чтобы зафиксировать настройки runreal MCP (`bRemoteExecution=True`, `RemoteExecutionMulticastBindAddress=0.0.0.0`). При этом в `Config/DefaultEngine.ini`, секция `[/Script/AndroidFileServerEditor.AndroidFileServerRuntimeSettings]`, лежал dev-токен `SecurityToken` (плагин **Android File Server**, AFS). Перед первым трекингом значение обнулено (`SecurityToken=`) — в git-историю реальный токен **не попадал** (коммит `f7542ad`); сквозной скан остальных `Config/*.ini` секретов не нашёл.

**Решение (правило):** секрет в репозиторий не кладём — независимо от публичности репо. Это не разовая мера, а постоянное правило для проектных конфигов под VCS.

**Остаточный риск (контингентный):** файл `Config/DefaultEngine.ini` теперь трекается. Если AFS-плагин активно используется, UE может **локально перегенерировать** `SecurityToken` → появится непустое значение, которое легко случайно закоммитить и запушить в публичный репо.

**Рассмотренные варианты защиты (ни один НЕ внедряется):**
- **(a) `git update-index --skip-worktree Config/DefaultEngine.ini` — ОТКЛОНЁН.** Обоснование: флаг локальный, **не переезжает на другую машину** (на ноуте защиты не будет), и **прячет легитимные правки** настроек этого файла (риск незаметно потерять/проглядеть нужное изменение конфигурации).
- **(b) Вынести AFS-секцию/токен в per-user конфиг вне VCS** — НЕ внедряется (см. статус).
- **(c) Отключить плагин AFS** — НЕ внедряется (AFS используется, см. статус).

**Статус: ЗАКРЫТО — риск принят, защита не вводится** (решение Рината, 2026-06-07). Спец-меры (a)/(b)/(c) не внедряем; `Config/DefaultEngine.ini` остаётся под VCS как есть, изменений в репозитории игры по этому поводу не делаем.
**Причина принятия риска:** Ринат использует WiFi-заливку на телефон через Android File Server (плагин нужен, отключать нельзя), а `SecurityToken` — **dev-only** (`bIncludeInShipping=False`) и работает **только в локальной сети**; ценность токена низкая, потенциальный ущерб от его раскрытия незначителен. Поэтому контингентный риск дрейфа токена в публичный репо принят осознанно.
**Действующее предупреждение (остаётся в силе):** репозиторий `Config/` **публичный** — настоящие секреты (ключи API, ключи подписи/keystore, облачные креденшелы, пароли) туда класть НЕЛЬЗЯ. Принятие риска касается исключительно низкоценного dev-токена AFS, а не секретов вообще.

## ADR-014 — protect-claude: PreToolUse-сторож рельсов от субагентов (best-effort, не airtight)
Контекст (Ш9 T2): включаем «тихий» режим (bare `Bash`/`PowerShell` в `permissions.allow`, без промптов) — человек выходит из петли подтверждений. Чтобы напарник/субагент не мог переписать собственные рельсы команды (хуки, settings, agent-дефы, git-хуки), добавлен PreToolUse-хук `.claude/hooks/protect-claude.ps1`.

**Механика.** Детект субагента — по полю `agent_id` в payload хука: оно присутствует **только** для вызовов субагента/напарника; главная сессия `claude --agent game-lead` его НЕ имеет (источник: code.claude.com/docs/en/hooks.md, 2026-06-09). Нет `agent_id` → exit 0 (пропуск). Есть `agent_id` + запись в защищённое дерево → exit 2 (block).
- **Защищённое множество:** всё под `.claude/**` и `.githooks/**` (суперсет явного списка из постановки — чтобы любой брошенный в `.claude` файл тоже резался). Карвут: `.claude/QA_OK` (маркер мерж-гейта) — точный финальный сегмент, traversal `QA_OK/../hooks` и суффикс `QA_OK_evil.txt` НЕ проходят.
- **Покрытие:** Write/Edit (по `file_path`) + Bash/PowerShell-команды (редиректы `>`/`>>` в защищённый путь, write-глаголы: Set-Content/Add-Content/Out-File/Tee-Object/New-Item/Remove-Item/Move-Item/Copy-Item/sed -i/cp/mv/rm + .NET WriteAllText/AppendAllText/StreamWriter/FileStream/::Create/::OpenWrite + tee/dd/truncate). Read-only (cat/Get-Content/git show) — пропускаются.
- Регистрация в `settings.json` `PreToolUse`, matcher `Edit|Write|Bash|PowerShell`. Настройки кешируются на старте сессии → **активируется только после рестарта**.

**Граница честности (важно — НЕ airtight).** Детект записи — это **denylist глаголов**, он принципиально неполон. Подтверждённые остаточные классы (qa, 2026-06-11):
- **Under-block (дыра):** inline-запись через интерпретатор — `python -c "open('.claude/..','w')"`, node `fs.writeFileSync` — НЕ ловится без ложных срабатываний на легитимных чтениях.
- **Over-block (fail-safe):** read-команда, буквально содержащая слова `tee`/`dd`/`install`/`truncate`/`create` И ссылающаяся на защищённый путь, → ложный block. Безопасная сторона (никогда не «ложно пропустить»), низкое влияние.

**Почему этого достаточно как слоя.** protect-claude — **defense-in-depth**, не единственная защита. Целостность `master` держится **независимо**: git-native pre-push/pre-merge хуки (T1) + маркер `.claude/QA_OK`, который создаёт **только** game-lead после «добро» qa. Напарники в `master` не пушат и не мёржат (ветка-политика + хуки), поэтому даже подмена рельсового файла в фиче-ветке не даёт напарнику протащить изменение в `master` — game-lead увидит diff до merge.

**Решение по остаткам:** НЕ чинить «точечным» анкорингом глаголов сейчас — это рискует ввести **under-block** (напр. `MSYS_NO_PATHCONV=1 rm .claude/...` при анкоринге по разделителям), что хуже fail-safe over-block. Оба остаточных класса вынесены в отдельный **follow-up** (вариант надёжного фикса — резолвить целевой путь записи / OS-level read-only ACL на `.claude/hooks` и `.githooks` для процесса агента, а не перечислять глаголы).

**Статус: ВНЕДРЕНО, прошло мерж-гейт qa** (ветка `feat/protect-claude-and-quiet`, коммит `13858c9`; qa ATTEST PASS с артефактом — харнесс 31/31, прогон против боевого хука). Активация — после рестарта сессии.

## ADR-015 — ContrarySurvivor: статы/выживание без GAS, на кастомном float-компоненте
**Контекст.** Диздок требует статы персонажа (Health, Hunger, Thirst, Money) и механику выживания (деградация голода/жажды, урон при истощении). UE-проект включает плагин GameplayAbilities (GAS), но в C++ он не используется — статы объявлены как «голые» float в классе персонажа, без системы.

**Решение (Ринат, 2026-06-11).** **GAS НЕ используем.** Статы и выживание реализуем через **лёгкий кастомный `UStatsComponent`** (`UActorComponent`) на обычных `float`:
- Поля: `Health/MaxHealth`, `Hunger/MaxHunger`, `Thirst/MaxThirst`, `Money`, `MoveSpeed`.
- Деградация Hunger/Thirst по таймеру (Tick/Timer), при пороге «критично» — деградация Health.
- Компонент **расширяемый под модификаторы статов** (структура модификаторов аддитив/мультипликатив) — чтобы при желании накинуть перки/баффы позже без переписывания. В MVP модификаторы используются только бронёй (защита) и снаряжением.
- Делегаты на изменение статов (`OnHealthChanged` и т.п.) для привязки HUD.

**Причина.** GAS даёт сетевую репликацию, GameplayEffects, теги — это избыточная сложность для одиночной (на MVP) игры с простыми статами и противоречит просьбе Рината «не усложнять». Кастомный компонент проще в отладке, дешевле по производительности (важно для Android), достаточен под текущий и обозримый скоуп. Прогрессия в игре — **через снаряжение, без XP** (см. ADR ниже по прогрессии в GDD ч.7.5), что снимает потребность в GAS-атрибут-сетах.

**Граница.** Если на пост-MVP появится мультиплеер или сложная система абилок — решение пересматривается (GAS может вернуться). Сейчас — кастом.

**Статус: ПРИНЯТО (Ринат, 2026-06-11).** Реализация — Фаза 1 (`UStatsComponent` базовый: Health + смерть; выживание Hunger/Thirst — Фаза 2). Источник правды по числам выживания — GDD ч.7.3 (черновые, утверждены на тюнинг).

## ADR-016 — ContrarySurvivor: World Partition отложен, старт на одной малой карте
**Контекст.** Диздок описывает большую основную локацию «Окрестности деревни» (~7-8 деревень по площади) + подлокации. UE 5.5 предлагает World Partition (стриминг большого открытого мира).

**Решение (Ринат, 2026-06-11).** **World Partition отложен.** Стартуем и ведём MVP на **одной малой карте**. Большой мир / стриминг вводим отдельной фазой построения мира (пост-MVP), когда контент и вертикальный срез готовы.
- Первый вертикальный срез (Фаза 1) — **маленький кусок «окрестностей деревни»** (решение Рината): простой уровень, 1-2 дома (пока кубы-заглушки), 1-2 дерева, 1-2 крупных камня, тест-арена под бой.

**Причина.** WP — это инфраструктура под масштаб, которого на MVP нет; раннее внедрение тормозит итерации и усложняет отладку. Малая карта достаточна для вертикального среза и ранних фаз. Переход на WP — обратимый рефакторинг уровней, не блокирует архитектуру геймплея.

**Статус: ПРИНЯТО (Ринат, 2026-06-11).**

## ADR-017 — ContrarySurvivor: абстракция ввода и наведения (ПК сейчас, тач Android позже)
**Контекст.** Цель — ПК + Android. Диздок: на ПК прицел/выбор цели мышью, на Android — виртуальные стики/кнопки и тап. Нужно не загнать архитектуру в мышь-специфику, чтобы потом не переписывать под тач.

**Решение (Ринат, 2026-06-11).**
- **Наведение через абстракцию «выбрать цель в точке экрана».** ПК: цель = актор под курсором мыши; клик ЛКМ = имитация тапа. Тот же путь («точка экрана → выбор цели/действие») переиспользуется для **тача Android** позже.
- **Первый срез — клик-захват цели** (выбрал кликом, цель держится при движении). Авто-захват ближайшего врага в радиусе ~5 м (диздок) — добавляем после первого среза.
- **Архитектуру ввода держим абстрактной** (Enhanced Input + слой «намерение действия», не привязанный к конкретному устройству). Реализация виртуального тач-UI Android — отдельная фаза.

**Причина.** Раннее разделение «устройство ввода ↔ игровое намерение» исключает дорогой рефактор при добавлении тача. Enhanced Input UE 5.5 уже даёт абстракцию маппинга; поверх — тонкий слой выбора цели по экранной точке, единый для мыши и тача.

**Статус: ПРИНЯТО (Ринат, 2026-06-11).** Реализация наведения/клик-захвата — Фаза 1.

## ADR-018 — ContrarySurvivor: модульность для ВСЕХ персонажей + runtime mesh merge как рычаг стоимости
**Контекст.** В Фазе 0 было зафиксировано «модульный меш — только у игрока; враги/NPC — единым склеенным мешем (Android: меньше draw call)». Ринат (2026-06-12) пересмотрел: модульность изначально проектировалась **на всех** персонажей — это объясняет, почему `Head/Torso/Legs` лежат в мастер-базе `AMasterHumanoidCharacter`, а не в `APlayerCharacter`.

**Решение (Ринат, 2026-06-12) — РАЗВОРОТ решения Фазы 0.** **Все персонажи (враги и дружественные NPC) — модульные** (Head/Torso/Legs из общей библиотеки частей на общем скелете). Спаунер врагов/NPC собирает персонажа из случайных/заданных модулей → дёшево в производстве + много визуальных вариаций из малого набора ассетов.

**Рычаг стоимости на Android — runtime skeletal mesh merge (склейка при спавне).**
- Авторинг/хранение — модульное (библиотека частей).
- Спаунер выбирает части → собирает → **при спавне склеивает в ОДИН скелетный меш** (UE Skeletal Merging: `USkeletalMergingLibrary` / `FSkeletalMeshMerge`) → **1 draw call** на персонажа, как у «единого меша», но собранного из модулей.
- **Враг/NPC** (снаряжение в рантайме не меняют) → merge один раз при спавне.
- **Игрок** (меняет броню вживую) → живые модульные компоненты, либо переклейка (re-merge) при смене экипировки.
- Итог: вариативность + дешёвое производство И стоимость одного меша на Android.

**Калибровка уверенности.**
- Модульность-для-всех + спаунер-сборка как практика — выведено/проверено (стандартный приём; совпадает с исходным замыслом Рината).
- Наличие Skeletal Merging **в UE 5.5** — НЕ подтверждено первоисточником на момент решения; **обязательна живая проверка cpp-dev/unreal-operator** (плагин Skeletal Merging) перед закладкой в код.
- **Фолбэк (если merge в 5.5 неудобен/недоступен):** живые модульные компоненты + Leader Pose Component (одна анимация) + LOD + разумный лимит одновременных врагов. Для MVP (мало врагов) приемлемо без merge.

**Влияние на архитектуру.** Отменяет рекомендацию «опустить модульность вниз в `APlayerCharacter`» (см. tech-design — снято). `AEnemyCharacter` наследует `AMasterHumanoidCharacter` **как есть** (модульные меши остаются в базе). Merge — отдельный слой/утилита, подключается как оптимизация (ориентир — когда врагов станет много, ~Фаза 3+); в Фазе 1 (1 бандит) — модульные компоненты без merge, не оптимизируем преждевременно.

**Самоограничения (чтобы держать «достаточно просто»):** ровно 3 слота (Head/Torso/Legs); смена = подмена целого меша слота; один общий скелет для всех вариантов всех слотов (дисциплина modeler-3d); части моделить внахлёст (без щелей на стыках).

**Статус: ПРИНЯТО (Ринат, 2026-06-12).** Дополняет GDD ч.2/ч.4/ч.7.4. Skeletal Merging в 5.5 — на живой проверке перед использованием.

## ADR-019 — ContrarySurvivor: версионирование /Content через Git LFS
**Контекст.** В гейм-репо `E:/ContrarySurvior/ContrarySurvivor/` (отдельный от team-репо, GitHub `RenchezLove/ContrarySurvivor`) папка `/Content` была в `.gitignore` → бинарные ассеты UE (.uasset/.umap) НЕ версионировались. Это блокировало мерж-гейт Фазы 1 (qa не мог ревьюить ассет-работу по git, нет истории/бэкапа ассетов). Перед merge нужно было выбрать механизм версионирования. Замер вживую: `/Content` = **1.8 МБ**, 26 `.uasset` + 1 `.umap`; `git-lfs 3.7.1` уже установлен.

**Решение (Ринат, 2026-06-13).** Версионируем `/Content` через **Git LFS**. Квота GitHub LFS (1 ГБ storage/bandwidth) при текущем размере — не проблема; рост по проекту контролируем, при нужде — data-packs.
- `.gitattributes`: `*.uasset`/`*.umap` (+ типовые бинарники `*.fbx/*.tga/*.png/*.jpg/*.wav/*.ogg/*.mp3`) → `filter=lfs diff=lfs merge=lfs -text`.
- `/Content` убран из `.gitignore`.
- `git lfs install --local` (хуки в гейм-репо).
- Контент закоммичен как LFS-указатели на ветке `feature/phase1-enemy-stats` (коммит `4fd95f4`); проверено `git lfs ls-files` = 27 файлов + `git show HEAD:...umap` отдаёт LFS-pointer.

**Решение по push (game-lead).** Пушим гейм-репо в GitHub с LFS **после** qa+merge — офсайт-бэкап + история ассетов.

**Калибровка.** Размер/наличие git-lfs — проверено вживую (du, git lfs version). LFS-трекинг — подтверждён артефактом (ls-files, pointer-формат). Квота на будущее — оценка, не замер.

**Статус: ПРИНЯТО (Ринат, 2026-06-13).** Гейм-репо. У team-репо своё версионирование (без LFS).

## ADR-020 — ContrarySurvivor: финальные модели в конце проекта + контракт ассета/тулинг рано (тулинг-трек JIT)
**Контекст.** Текущие модели (игрок `HumanoidCharacter`, бандит) — препродакшн/грубые. Вопрос Рината: когда делать качественные (game-ready) модели — в конце MVP или в конце всего проекта; и как вести инструментарий (Master-классы оружия, prop-киты деревьев/камней/мусора, конструкторы заборов/брошенных авто и т.п.), который упрощает разработку и ручное редактирование проекта.

**Решение (Ринат, 2026-06-13).**
1. **Финальные качественные модели — в КОНЦЕ всего проекта** (выделенный связный арт-пасс после лока механик/контента), НЕ в конце MVP. Причина: полировать визуал поверх неустаканенных механик = выброшенная работа; один пасс в конце = визуальная консистентность. До этого — препродакшн/плейсхолдеры, лишь бы читался силуэт и фракция.
2. **«Контракт ассета» + конвенции — фиксируем РАНО** (единый масштаб/единицы, пивоты/origin, сокеты, скелет `RootAnim`, топология швов модулей, именование, структура `/Content`). Дёшево, окупается на всех фазах и в ручном редактировании Рината; делает поздний арт-пасс «подстановкой» без интеграционной боли (грубый меш ↔ финальный меняется почти бесплатно).
3. **Инструментарий — сквозной трек по принципу JIT (Just-In-Time):** инструмент/кит делаем НЕ заранее «про запас», а когда фаза ВПЕРВЫЕ упирается в этот класс ассетов И паттерн повторяется (нужен >1 раза). НЕ отдельная большая фаза-стройка и НЕ выделенный спринт — маленькие переиспользуемые deliverable по ходу фаз. Владельцы: `cpp-dev` (Master-классы оружия — база `AMasterWeapon` уже есть), `modeler-3d` (Blender prop-киты), `unreal-operator`/будущие `tech-artist`+`level-designer` (BP-конструкторы, spline-инструменты, процедурная расстановка).

**Следствие для бандита.** Отдельный слот «полировка визуала бандита» НЕ заводим — недоделанный визуал (цвет/границы зон, размер кепки) входит в общий финальный арт-пасс конца проекта как backlog-пункт.

**Калибровка.** Это план-решение Рината (не технический факт). «Контракт рано / финал поздно» — отраслевая практика (выведено), согласовано Ринатом.

**Статус: ПРИНЯТО (Ринат, 2026-06-13).** Формализуется в roadmap.md (тулинг-трек + финал-арт-пасс) и tech-design.md. Документ конвенций («контракт ассета») — грунтуется на реальном проекте отдельной задачей (не выдумывать значения).

## ADR-021 — Headless UE-операции через UnrealEditor-Cmd (канал/MCP-независимый путь)
**Контекст.** unreal-MCP канал (Remote Execution) хронически флакки: «No command channel open», инжект тулзов в свежие субагенты теряется, восстановление требует `/mcp` reconnect Рината (вне инструментов game-lead). Нужен путь для ДЕТЕРМИНИРОВАННЫХ ассет-операций без зависимости от живого MCP-канала.

**Решение/находка (подтверждено живьём 2026-06-13, Фаза 3).** Для импорта/правки ассетов использовать **headless-коммандлет**:
`UnrealEditor-Cmd.exe "<uproject>" -ExecutePythonScript="<abs .py>" -unattended -nopause -nosplash`
- Работает с ЗАКРЫТЫМ редактором, поднимает свой временный инстанс, исполняет `unreal`-python, гасится. MCP/`/mcp` НЕ нужны → не зависит от Рината.
- Подтверждено: импорт 13 FBX (static/skeletal/anim) + дублирование/назначение материала + верификация (`has_vertex_colors`, skeleton-binding) на ветке `feature/phase3-combat` (коммит `f1c01f2`).
- Аналог headless-Blender у modeler (`blender.exe -b --factory-startup --python`) — обе роли имеют MCP-независимый CLI-путь.

**Нюансы/границы.**
- **stdout ПУСТ** на Windows (UE-Cmd не пишет в пайп/`tee`) → весь вывод python в `Saved/Logs/<Project>.log` (маркеры-префиксы в логах для поиска). Пруф брать оттуда, не из stdout.
- Импорт идёт через **Interchange** (`InterchangeAssetImportData`) — часть legacy-свойств с ассета не читается; наличие данных проверять прямыми API (`has_vertex_colors`), не настройками импорта.
- struct-массивы материалов (`static_materials`/`materials`) отдают КОПИЮ — назначение требует assign-back (`mats[i]=elem`) + повторное сохранение.
- **НЕ headless-friendly:** редактирование графов AnimBP/Blueprint Event Graph, арт-расстановка на уровне «на глаз», Play-проверка — остаются editor/супервайз-этапом.

**Приоритет инструментов (уточнение к «нативное первым»):** для ассет-операций UE — (1) live MCP если канал жив; (2) **headless-коммандлет (этот ADR)** когда канал флакки/недоступен; (3) Computer Use крайний случай.

**Статус: ПРИНЯТО/НАХОДКА (2026-06-13).** Применять для детерминированных ассет-операций без зависимости от `/mcp`.

## ADR-022 — Каталог ассетов: папки-источник + генерируемая HTML-витрина (не ручная таблица)
**Контекст.** Ринату нужно быстро и наглядно смотреть ассеты (скриншот, описание, поликаунт, путь), не открывая Blender/UE по одному. Вопрос: вести ли реестр и как, чтобы это не создавало ручную нагрузку и риск галлюцинаций (устаревшие цифры, выданные за факт).

**Решение (Ринат, 2026-06-19).**
1. **Каталог = папки в git.** На каждый ассет — подпапка по имени ассета в `assets/<asset_id>/`. Внутри: модель-источник (`.blend`), рендер-превью (`.png`), сайдкар-описание (`<id>.asset.md`). Папки и есть каталог (источник правды по ассету).
2. **Сайдкар пишет `modeler-3d`** (автор ассета). Руками заполняется ТОЛЬКО невыводимое: описание, статус (`preview`/`game-ready`), теги. Механика (faces, tris, bbox, материал, путь) — реально проверенные из `.blend`, не по памяти.
3. **Витрина — один статичный HTML-файл** (`assets/index.html`), сетка карточек: тумбочка + описание + поликаунт + путь. Открывается двойным кликом локально, без сервера/CDN. Формат HTML выбран Ринатом (нагляднее markdown).
4. **Витрина — производное, не источник.** Никто не доверяет её цифрам как факту и НЕ копирует их в `context.md`; за фактом идём в файл/движок. Снимает риск галлюцинаций: данные тянутся из файлов, а не из памяти/ручной таблицы (ручную таблицу отвергли именно из-за дрейфа).
5. **Авто-генератор витрины — по JIT** (ADR-020 §3): скрипт, который сканит `assets/*/`, читает сайдкары и пересобирает `index.html`, пишем, когда ассетов станет несколько и паттерн повторится. Пока ассет один — витрина собрана вручную как seed, который позже заменит генератор.
6. **UE даёт каталог для game-ready** (Content Browser: тумбочки + tris). Наш каталог ценен прежде всего для исходников в Blender и для взгляда «не открывая UE».

**Связь с ADR-020.** Это часть «контракта ассета + конвенций рано». Структура `assets/<id>/` и поля сайдкара — кандидаты в документ конвенций.

**Калибровка.** План-решение Рината (не технический факт). «Генерируемое вместо ручного» — следствие правила «единый источник, не дублировать» (CLAUDE.md).

**Статус: ПРИНЯТО (Ринат, 2026-06-19).** Применяется начиная с ассета `iron_barrel`.

**Уточнение (game-lead, 2026-06-25):** для ассетов, собранных в МУЛЬТИобъектном Blender-файле (один `.blend` строит несколько мешей — напр. `banditprops`=4, `vegetation`=7, `grasstuft`=2), физический `.blend` в каждую `assets/<id>/` НЕ копируется (это дубли + раздувание git + риск рассинхрона). Вместо этого сайдкар ссылается полями `source_model`/`builder` на единый QC-бленд и билдер в рабочем источнике (`demo-assets/_build/`) — единый источник правды, уже под контролем. Одиночные ассеты (как `iron_barrel`) держат `.blend` в своей папке, как и было. Дух ADR (источник правды доступен, не дублируется) сохранён. Применено при наполнении реестра демо-серией ContrarySurvivor (17 ассетов, 2026-06-25).

## ADR-023 — ContrarySurvivor: структура /Content = feature-first (Lyra-стиль)
**Контекст.** `/Content` смешивал две схемы: «по типу» (`Blueprints/`, `Materials/`) и «по фиче» (`Characters/Wolf/` — меш+анимации вместе). Гибрид → непоследовательность (факт, листинг дерева 2026-06-22): BP бандита в `Blueprints/Enemies/`, у волка BP нет вовсе, `BP_Campfire` оторван от своих мешей (`Environment/Misc`), оружие/системные BP свалены в `Blueprints/`.

**Решение (Ринат, 2026-06-22).** Приводим `/Content` к **feature-first** (как Epic Lyra): всё про одну сущность — в одной папке. Единое правило вместо гибрида.
- `Characters/{Player,Elder,Trader,Bandit,Wolf,Shared}` — каждая сущность со своими мешами/анимами/BP; `Shared/{Humanoid,Armor,Clothing}` — общий каркас модульного гуманоида (бывш. `TestContentAndCode/` — продакшн-ассеты вынесены из папки с именем «Test»).
- `Weapons/{Pistol,Knife}`.
- `Environment/{Buildings,Nature,Props/Campfire,Props}`.
- `System/` — `BP_GameMode`, `BP_PlayerController`.
- **Общими категориями оставлены** (НЕ растащены по фичам — решение Рината): `Audio/`, `Materials/`, плюс `Maps/`, `UI/`, `Input/`. Причина: кросс-каттинг + многие жёстко прописаны в C++; растаскивание = лишние правки путей+пересборки без пользы. В Lyra звук тоже общий.

**Метод переноса.** Только через UE (rename/move + чистка редиректоров), не файловым `mv` — иначе рвутся ссылки (см. ADR-021). Жёсткие строковые пути ассетов в C++ (`FObjectFinder`/`FClassFinder`) и в `Config/*.ini` Fix Up Redirectors НЕ чинит — правятся вручную + пересборка. Проверено грепом (2026-06-22): в C++ ~8 хардкод-путей на перемещаемые ассеты (7 файлов); в `Config` — только дефолтная карта `L_World` (в `Maps/`, не двигается).

**Калибровка.** Единой обязательной раскладки Epic не навязывает; ориентир — UE Style Guide (Allar) + сэмплы Epic (Lyra). Ключевое правило — последовательность (одна схема). План-решение Рината.

**Статус: ПРИНЯТО (Ринат, 2026-06-22).** Выполняется батчами на ветке `feature/clean-village` (батч 1 — карты/пропы/оружие — закоммичен `e06e6a0`, PIE-подтверждён Ринатом). Целевое дерево — в `docs/contrary-survivor/tech-design.md`.

## ADR-024 — ContrarySurvivor: на уровень ставим BP-наследников C++; базы врагов = `AMasterEnemyBase` (сабсистемы спавна удаляются)
**Контекст.** Спавн волков/бандитов сейчас — два `UWorldSubsystem` (`WolfSpawnSubsystem`, `BanditSpawnSubsystem`; бандитский — «зеркало» волчьего, дублирование). Слабые места (факт чтения кода 2026-06-22): сабсистема — не актор, её НЕЛЬЗЯ поставить/увидеть в уровне; локация базы (`BanditBaseLocation`/`WolfDenLocation`) фактически берётся из C++-дефолта (EditAnywhere на сабсистеме в level-редакторе не показывается); волк спавнится голым C++-классом `AWolfCharacter` без BP.

**Решение (Ринат, 2026-06-22).**
1. **Конвенция:** всё, что ставится/спавнится на уровне, — **BP-наследник соответствующего C++-класса** (логика в C++, BP ставится и тюнится в уровне; рекомендация Epic). Закрывает пробел: создаём `BP_Wolf : AWolfCharacter`; бандит уже `BP_EnemyBandit`.
2. **Базы врагов — размещаемый актор, не сабсистема.** Один параметризуемый C++-родитель **`AMasterEnemyBase`** (база/лагерь = точка спавна по приближению: триггер-радиус, набор мешей, что/сколько спавнить, опц. квест-предмет). От него — BP-наследники `BP_BanditBase`, `BP_WolfDen`. Даёт: визуальное размещение в уровне, **несколько баз** в мире, настройку каждого экземпляра (число врагов/радиус/меши) + BP-варианты для разнообразия; убирает дублирование волк/бандит. Имя `AMasterEnemyBase` = вражеская база/лагерь (место спавна), НЕ сам враг.
3. **Обе сабсистемы (`WolfSpawnSubsystem`, `BanditSpawnSubsystem`) — на удаление** после переноса логики в `AMasterEnemyBase`.

**Тайминг.** Код-рефактор уровня **Этапа A** — ПОСЛЕ Этапа 0 (геймлуп проверяется на текущих рабочих сабсистемах) и ПОСЛЕ механического реорга папок (ADR-023). Не смешивать с реоргом (одна переменная за раз).

**Калибровка.** «Сабсистема не размещается/не видна в редакторе, локация из C++-дефолта» — следствие природы `UWorldSubsystem` (нет трансформа, не в Outliner; проверено чтением кода). Выбор паттерна — решение Рината, согласуется с Epic-практикой для размещаемых энкаунтеров.

**Статус: ПРИНЯТО (Ринат, 2026-06-22).** Реализация — Этап A демо-плана. Канон вражеских лагерей — GDD; план — `demo-plan.source.md`.

Тех-долг сейва (`ItemName`/`StackCount`) — ОТЛОЖЕН к E2/DataTable.
**ФИНАЛ попапа готов (concept, 06-24):** `docs/contrary-survivor/ui/death-penalty-popup.final.{png,html}`. Текст: заголовок **«ВЫ ПОГИБЛИ»** (череп) / подзаг «Возрождение у костра в деревне.»; **«−40% монет»** («Часть монет утрачена при гибели.»); **«Расходники обронены на месте гибели»** («Все расходники выпали мешком на месте гибели — их можно забрать.»); зелёная плашка **«Снаряжение, оружие и важные предметы сохранены.»**. cpp берёт этот текст в `DrawDeathScreen` (A4). **+ Задача A4/HUD:** валюта в HUD `₽`→«монеты» (лейбл + иконка без глифа ₽), чтобы HUD и попап совпадали.
**Статус: РАЗВЕДАНО, ВСЕ решения приняты (вкл. финальный текст попапа), A4 полностью разблокирован; реализация — после A5.**

## ADR-028 — ContrarySurvivor: команда делает ИНСТРУМЕНТЫ, расстановку Ринат делает сам; геометрия и пропсы баз — ВНУТРИ их Blueprint'ов (Ринат, 2026-06-25)
**Решение Рината.**
1. **Команда делает готовые инструменты, а финальную расстановку по уровню Ринат делает сам.** «Инструменты» = готовые ассеты в проекте: дома, собранные базы-блюпринты, пропсы, растительность в папке Content. Раскладку растительности (кисть Foliage) Ринат тоже делает сам, либо попросит отдельно, либо обойдётся без неё. `game-lead` НЕ расставляет декор по своей инициативе и НЕ ставит модели отдельными актёрами по уровню.
2. **База врага собирается как ОДИН Blueprint, чтобы двигать целиком.** Вся геометрия базы и её пропсы добавляются **компонентами ВНУТРЬ соответствующего Blueprint'а**:
   - `BP_WolfDen` (логово, наследник `AMasterEnemyBase`, ADR-024): пещера `SM_WolfDenCave` + кости `SM_BonePile`.
   - `BP_BanditBase` (база бандитов): сарай `SM_BanditShed` + костёр `SM_BanditCampfire` + ящики `SM_BanditCrate` + бочки `SM_BanditBarrel` + забор `SM_BrokenFence`.
   Это НЕ отдельные актёры на уровне. Тогда Ринат двигает базу одним актором, и пропсы едут с ней.
3. **Дома** (`SM_VillageHouse`) — общий ассет; 6 размещённых домов = экземпляры одного ассета, обновляются разом одним реимпортом.
**Следствие для Фазы B:** работа `game-lead` = (1) завести меши в проект, (2) собрать базы-блюпринты (меши+пропсы внутрь BP), (3) заменить дом реимпортом, (4) импортировать растительность в Content. Расстановка флоры и тонкая раскладка по уровню — за Ринатом.
**Статус: ПРИНЯТО (Ринат, 2026-06-25).**

## ADR-029 — ContrarySurvivor: спавн врагов — число НЕЗАВИСИМО от числа точек спавна (Ринат, 2026-06-25, PIE-фидбек)
**Контекст.** Первая реализация `AMasterEnemyBase` (ADR-024, Фаза B): точки спавна = компоненты `UEnemySpawnPointComponent` (видимые/двигаемые стрелки в BP), и спавнится РОВНО по одному врагу на каждую точку (число врагов = число точек). Ринат в PIE проверил: разместил вторую базу бандитов, выставил «спавнить 5» — заспавнилось всё равно 3 (т.к. в BP 3 точки). Жёсткая привязка «1 точка = 1 враг» мешает менять число врагов на размещённом экземпляре BP.
**Решение (Ринат, 2026-06-25).** Развязать число врагов от числа точек:
- В BP базы держать БОЛЬШЕ точек, чем нужно по дефолту (ориентир ~7) — это «ёмкость»/возможные позиции, которые дизайнер двигает.
- Добавить отдельный `EditAnywhere`/`BlueprintReadWrite` параметр **`NumToSpawn`** (дефолт C++ = 3; в BP_WolfDen выставить 4, в BP_BanditBase 3) — сколько врагов реально спавнить.
- Спавн-логика спавнит `NumToSpawn` врагов, используя `NumToSpawn` точек из доступных (первые N либо случайное подмножество). Если `NumToSpawn` > числа точек — не больше, чем есть точек.
- Так дизайнер на КАЖДОМ размещённом экземпляре базы задаёт число врагов числом (не добавляя/удаляя точки).
**Связанные пункты PIE-фидбека (в плане доводки, см. `context/game-lead/context.md` «СЕЙЧАС»):** `ActivationRadius` визуализировать в вьюпорте (BP и мир); наши кастомные UPROPERTY поднять выше в Details-панели (после Transform) во всех наших BP; кровь-декаль сделать органической формы (текстура с альфой) и не красить проходящих акторов.
**Статус: ПРИНЯТО (Ринат, 2026-06-25); реализация — следующая сессия (cpp + game-lead).**

## ADR-030 — ContrarySurvivor: финальный гейт Фазы B — «лёгкая» проверка вместо формального qa-агента (Ринат, 2026-06-25)
**Контекст.** Вся доводка Фазы B (спавн/декали/костёр/навмеш/земля/огонь) проверена и принята Ринатом ЛИЧНО в живом PIE по ходу сессии. Встал вопрос: гонять ли перед merge в master формальный qa-агент. Ринат опасался, что «qa может что-то сломать».
**Решение (Ринат).** Для этой ситуации (Ринат лично всё принял в PIE) формальный qa-агент НЕ запускаем. Вместо него финальный гейт = **(1) ОДНА чистая сборка всей ветки** (убедиться, что весь C++ компилируется вместе) **+ (2) финальный взгляд Рината в PIE** → **merge `feature/clean-village`→master**. 
**Уточнение (важно, зафиксировано):** qa-агент по своей роли НИЧЕГО не редактирует — он только читает/собирает/гоняет тесты (инструменты Read/Glob/Grep/Bash; роль = верификация). «Сломать» рабочие ассеты/код он не может. Опасение Рината снято разъяснением.
**Граница.** Это НЕ отмена qa-гейта как института. Когда фичу НЕ принимал лично Ринат (или меняется боевой/рисковый код, или несколько разработчиков), формальный qa + маркер `.claude/QA_OK` остаются в силе (CLAUDE.md «Ветки и QA-гейт»). Лёгкий гейт — для случая «Ринат сам всё отсмотрел вживую». В гейм-репо тех-хука гейта нет (политику веток game-lead держит вручную); merge в master — только после чистой сборки + PIE-добра Рината.
**Статус: ПРИНЯТО (Ринат, 2026-06-25).** Применить при завершении Фазы B (след. сессия, после сборки дальности отрисовки).

## ADR-031 — ContrarySurvivor: ручную «дальность отрисовки» НЕ делаем — опора на встроенный frustum culling (Ринат, 2026-06-26)
**Контекст.** Планировался единый параметр «дальность отрисовки» (`RenderDistance` на `APlayerCharacter`): число → `SetCullDistance`/`SetCullDistances` всем мешам/Foliage + визуализатор границы. Реализовали и собрали (визуализатор пробовали сферой вокруг игрока, затем пирамидой `UDrawFrustumComponent` от камеры).
**Проблемы (вскрылись в PIE-проверке Рината).** (1) Cull-дистанция в UE считается ОТ КАМЕРЫ, а top-down камера ~30 м (3000 см) позади/выше игрока → сфера-визуализатор «вокруг игрока» вводит в заблуждение (радиус сферы ≠ реальная граница), при R<~3000 близкие объекты режутся. (2) Родной `UDrawFrustumComponent` рисуется ТОЛЬКО при включённом show-флаге вьюпорта «Camera Frustums» (по умолчанию выкл; пруф по исходникам движка `DrawFrustumComponent.cpp:124` + `ShowFlags.h:424`) → «видно сразу» не даёт. (3) Главное (вывод Рината): **движок Unreal и так не рисует то, что вне кадра камеры (view frustum culling) — встроенно, бесплатно, всегда включено.** Для top-down с узким обзором это и есть нужная оптимизация; ручной distance-cull даёт мало.
**Решение (Ринат).** Ручную дальность отрисовки + визуализатор УБРАТЬ полностью; опираться на встроенный frustum culling. Дальнюю растительность при необходимости резать штатным **Foliage cull distance** (настройка Foliage type), а не своим кодом. Обзор (сколько мира видно) регулируется КАМЕРОЙ (`CameraArmLength`/`FOV` в `BP_PlayerCharacter`), а не «дальностью отрисовки» — это разные вещи.
**Реализация.** `PlayerCharacter.h/.cpp` откатаны к состоянию до render-distance (коммит `2000cfe`, −107 строк); пересборка `BUILD_EXIT=0` (лог `context/cpp-dev/logs/phaseB-renderdistance-revert-build.log`). В `master`.
**Статус: ПРИНЯТО и РЕАЛИЗОВАНО (Ринат, 2026-06-26).**

## ADR-032 — ContrarySurvivor: материалы моделей — vertex color по умолчанию (не текстуры)
**Контекст.** Вопрос Рината (2026-06-26) по ножу: для оптимизации — один материал + текстура с UV-развёрткой? Текущие ассеты проекта (оружие, пропсы, дом, природа) сделаны на **vertex color** (vcol): 1 материал, нода VertexColor 'Col' → BaseColor; UV-развёртка есть, но текстура не используется (цвет хранится в вершинах).
**Решение (game-lead, подтверждено как конвенция).** Для game-моделей по умолчанию — **vertex color, без текстур**: 1 материал на ассет, плоские цвета зон в вершинах. Причина: низкополи плоский стиль + камера top-down/изометрия (модели на экране мелкие, детали текстуры не читаются) + цель слабый Android (vcol = ноль текстурной памяти, минимум draw call). UV-развёртка на моделях ОСТАВЛЯЕТСЯ (на будущее: если конкретному ассету понадобится текстура/детали — добавляется без переделки геометрии).
**Граница.** Текстура с UV вводится ТОЧЕЧНО, только если ассету реально нужны детали, которых vertex color не даёт (для текущего демо-контента — не нужно). Иконки инвентаря/HUD — это 2D-рисунок (PNG), отдельный пайплайн (concept code-render), к материалам моделей не относится.
**Статус: ПРИНЯТО (конвенция, 2026-06-26).** Подтверждено фактом: `assets/knife/knife.asset.md` (material M_Knife, vcol). Применяется ко всем game-моделям проекта.

## ADR-035 — ContrarySurvivor: камера — два режима (исследование look-ahead / бой — смещение к угрозе, без зума) (Ринат, 2026-07-01)
**Контекст.** Бандитам добавляется огнестрел (demo-plan-v2 D6). Вводится правило честности «враг не стреляет по игроку, если он вне кадра камеры» → камера становится **границей честности**: что на экране, то и может по тебе стрелять. Текущая камера — изометрия + лёгкий look-ahead (смещается в сторону движения). В бою при отходе спиной стрелки уходят за кадр.
**Решение (Ринат).** Камера — ДВА режима:
1. **Исследование:** лёгкий look-ahead (как сейчас) — камера чуть впереди по ходу движения.
2. **Бой:** камера ПЕРЕСТАЁТ смотреть вперёд и слегка смещается к ближайшей угрозе (или к центру угроз), чтобы всё, что может стрелять по игроку, было в кадре. **БЕЗ отдаления/зума** (зум = перф-налог на слабом Android: шире кадр = больше объектов). Плавно, без рывков, не «драться» с большим пальцем игрока.
3. **Краевые индикаторы:** переиспользовать существующий механизм краевых стрелок HUD (`DrawNPCEdgeArrow`/`DrawNPCMarker`, категория `HUD|NPCMarker`) как отдельный маркер «стрелок» для редких случаев «за кадром».
**Зачем.** Игрока не убивают «из-за края». Плюс — защита валидности теста удержания: нечестная камера занижает D1/D7 и мажет сигнал.
**Стоимость (калибровка).** Боевой режим — НОВЫЙ код камеры (детект боя + выбор угрозы + плавное смещение): УМЕРЕННО; перф — ДЁШЕВО (без зума). Краевые стрелки — существуют (проверено по коду `ContrarySurvivorHUD.h`, `DrawNPCEdgeArrow`) → реюз ДЁШЕВО (сейчас Canvas/DrawHUD; UMG-миграция отложена). Финальная «на ощупь» доводка — плейтест (Ринат в PIE).
**Связь.** Делается ВМЕСТЕ с огнестрелом бандитов (D6). Боевая камера + «поводок» ИИ (ADR-036) + правило «вне кадра не стреляет» вместе закрывают и кайтинг-эксплойт, и вторжение в деревню.
**Статус: ПРИНЯТО (Ринат, 2026-07-01).** Реализация — пакетом с огнестрелом бандитов (D6), **в Build 1** (Ринат 07-01: без огнестрела бандиты = копия волков, оба только вплотную).

## ADR-036 — ContrarySurvivor: поведение врагов — «поводок» у базы + безопасная деревня (Ринат, 2026-07-01)
**Контекст.** Нужно закрыть кайтинг («увильнул спиной — и безнаказанно») и сделать деревню читаемо-безопасной, а не «невидимой стеной». Факт по коду (`EnemyAIController`): погоня гейтится только `DetectionRange` (1500 см) + `LineOfSightTo`; базового «поводка» (возврат к базе) НЕТ. Обход деревни задуман на уровне навигации: классы `UNavArea_Village` + `UNavQueryFilter_ExcludeVillage` в коде ЕСТЬ и ИИ их применяет (проверено по исходникам). НО размечена ли зона деревни объёмом (Nav Modifier Volume) на карте `L_World_C` — **НЕ ПРОВЕРЕНО** (проверить в редакторе/PIE). Подход как задумано: навмеш на всю карту + пометить деревню зоной-исключением. Дыра: у ИИ есть fallback прямой погони (`AddMovementInput`, игнорирует навмеш) → nav-исключение деревни его НЕ останавливает (нужен явный запрет по границе). (Отдельно: `SafeZoneTrigger` на костре — это АВТОСЕЙВ-зона, радиус 300 см, к избеганию врагов отношения не имеет.)
**Решение (Ринат).**
1. **Поводок у базы:** враги базы гонятся за игроком в пределах разумного радиуса от СВОЕЙ базы; ушёл далеко → разворачиваются и возвращаются, НЕ гонятся до последнего. Волки — так же к логову. Внутри поводка ДОГОНЯЮТ (закрывает кайтинг); полный отход игрока = валидная тактика «драться/бежать» (фича, не баг).
2. **Деревня = безопасная зона:** враги в неё НЕ заходят. Гонясь, у границы деревни ЗАМЕДЛЯЮТСЯ, стоят пару секунд и уходят обратно — чтобы читалось «не пойдёт в деревню», а не «упёрся в стену». Должно работать и при прямой погоне (fallback), не только на навмеше.
3. Часто граница поводка и граница деревни совпадают — настроить, чтобы совмещались.
**Стоимость (калибровка).** Поводок — НОВЫЙ (нет в коде): дом-точка (из спавнера `AMasterEnemyBase`) + макс-радиус + возврат; ДЁШЕВО-УМЕРЕННО. Безопасная деревня — обход по навмешу ЕСТЬ (реюз `NavArea_Village`); НОВОЕ = поведение у границы (замедление/пауза/возврат) + перекрыть дыру прямого fallback (проверка границы деревни и в direct-режиме): УМЕРЕННО. ⚠️ НЕ ПРОВЕРЕНО: заходит ли сейчас прямой fallback в деревню (вероятно да, т.к. игнорирует навмеш) — проверить в живом PIE.
**Связь.** Полезно и БЕЗ огнестрела (даже для ближников) → можно раньше D6. Вместе с боевой камерой (ADR-035) и правилом «вне кадра не стреляет» — цельная честная система боя.
**Статус: ПРИНЯТО (Ринат, 2026-07-01).** Реализация — Группа 1, **Build 1** (вместе с D6).

## ADR-037 — ContrarySurvivor: плотность боя ≤2–3 активных врага + нож = передний сектор (отменяет радиусный 360°) (Ринат, 2026-07-01)
**Контекст.** Для LDoE-ощущения (вдумчивый читаемый бой), честности по новой боевой камере (ADR-035) и валидности теста удержания нужно ограничить хаос. Плюс прежний ПЛАНИРУЕМЫЙ вариант «холодное = радиусный урон 360°» (ADR-планируемые 06-26; demo-plan D3) для приземлённого survival-ножа читается аркадно.
**Решение (Ринат).**
1. **≤2–3 активных врага одновременно.** Стая/группа МОЖЕТ существовать (4 волка у логова), но вступает в бой ВРАСТЯЖКУ — через ЭНКАУНТЕР-ДИЗАЙН (радиус агра, расстановка, тропы; связано с «поводком» ADR-036 и точками спавна `AMasterEnemyBase`), а НЕ «убрать половину волков». Бандиты (3) уже почти в рамках.
2. **Нож = передний взмах/сектор:** задевает 1–2 цели ВПЕРЕДИ (несколько за удар — ок), но **НЕ круговой 360° урон вокруг игрока**. Это **ОТМЕНЯЕТ** планируемый «радиусный урон холодного».
3. Если на плейтесте нож слаб против 2–3 — **расширить передний сектор, НЕ делать круг**.
**Причина.** Круговой AoE — механика жанра толпы; для приземлённого survival-ножа 360° читается аркадно/неестественно. Меньше активных врагов = читаемо, честно под боевой камерой, чище сигнал теста (игрок реагирует на «ядро», а не на несправедливый хаос).
**Стоимость (калибровка).** Нож передним сектором ≈ той же цены, что радиусный (замена формы проверки sweep/overlap — не круг, а сектор впереди): ДЁШЕВО. Плотность ≤2–3 — в основном энкаунтер-дизайн/тюнинг агро-радиусов и «поводка» (ADR-036), кода немного: ДЁШЕВО-УМЕРЕННО. ⚠️ НЕ ПРОВЕРЕНО текущая форма удара ножа в коде (`AMeleeWeapon`) — сверить при реализации.
**Статус: ПРИНЯТО (Ринат, 2026-07-01).** Реализация — Фаза D (demo-plan-v2), Build 1. Отменяет планируемый пункт «холодное оружие = радиусный урон» (помечен ниже как отменённый).

## ADR-039 — ContrarySurvivor: качание растительности через материалы (WPO) + границы headless-редактирования материалов в UE 5.5 Python (2026-07-02)
**Контекст.** Ринату нужно лёгкое покачивание травы, деревьев, белья на верёвке и брезента тента. В UE НЕТ галки «ветер» — качание задаётся в МАТЕРИАЛЕ через World Position Offset (WPO, сдвиг вершин). Нативный экономный путь (подтвердил Ринат) — материал, а не отдельная система; дёшево для слабого Android.
**Решение (техника ветра).**
1. Узел **`SimpleGrassWind`** (`/Engine/Functions/.../WorldPositionOffset/SimpleGrassWind`) → в World Position Offset. Входы `WindIntensity`,`WindWeight`(=1.0),`WindSpeed`,`AdditionalWPO`(=Constant3Vector 0,0,0) — **ВСЕ обязательны** (иначе `Error: Missing function input` → материал падает на дефолт-шахматку). `WindIntensity`/`WindSpeed` вынесены в ScalarParameter (группа Wind) для настройки.
2. **Профиль качания = ×маска по высоте.** Низ неподвижен, верх качается: `LocalPosition`→ComponentMask(Z)→нормировка→Saturate. Для авто-нормировки под ЛЮБУЮ высоту меша — `MaterialExpressionObjectLocalBounds` (выходы **`Min`**/**`Max`**). Инверт (верх стоит, низ качается — бельё) = `(topZ - Z)/drop`.
3. **Только горизонталь** (чтоб не уходило под землю) = ×`Constant3Vector(1,1,0)`.
4. **Разделение в одном меше** (ткань vs дерево, полотно vs опоры): маска по **яркости vertex-color** (dot с 0.333) или по **высоте ступенькой**. Разные меши с разным поведением → ОТДЕЛЬНЫЕ материалы.
5. Материалы демо: `M_GrassWind` (трава, height-маска кончиков), `M_ClothesWind` (бельё, яркость×инверт-высота), `M_AwningWind` (тент, ступень-маска — полотно синхронно, опоры стоят), `M_WindTrees` (деревья, ObjectLocalBounds). Обрезка дальней травы — штатный foliage cull distance (6000→9000 под камеру 3000), НЕ свой код (в русле ADR-031).
**Границы инструмента (важно, проверено 07-02).** Headless-Python (MCP `editor_run_python`) в UE 5.5 **НЕ умеет надёжно редактировать граф материала:**
- Вход **World Position Offset НЕ выведен** в Python (`unreal.MaterialProperty` без WPO; `connect_material_property` его не видит) → финальный провод «ветер → WPO» подключает **только человек вручную** в редакторе материала.
- **Перечислить узлы** существующего материала из Python нельзя (нет доступа к expression list).
- `delete_all_material_expressions` чистит **НЕ полностью** (оставляет узлы) → правка существующего материала вслепую плодит мусор.
- После `reload_packages`/удалений **реестр глючит**: `does_asset_exist`/`find_package_referencers` врут, `delete_asset`=False. Истина по материалу меша = `sm.get_material(i)` (живое чтение), не реестр. Чистка мусора+фантомов — после ПЕРЕЗАПУСКА редактора.
**Рабочий приём:** материал-с-ветром собирать НОВЫМ дубликатом базового (`AssetToolsHelpers.get_asset_tools().duplicate_asset(name,path,object)` — по объекту, устойчиво к глюку реестра) + добавлять узлы add-only, держа ссылки в ОДНОМ скрипте; финальный провод в WPO — вручную Ринат.
**Дополнение (проверено 2026-07-05, пруф — фикс дыма `d144d10` гейм-репо):** правка СВОЙСТВ уже существующих нод материала headless РАБОТАЕТ: обход графа от корня (`MaterialEditingLibrary.get_material_property_input_node` → `get_inputs_for_material_expression`) возвращает живые ссылки на ноды; `node.set_editor_property('texture', tex)` + `recompile_material` + `save_asset` — применяется и сохраняется. Ограничение «перечислить узлы нельзя» касается плоского списка expressions; обход от подключённого корня — можно (отвязанные от корня ноды так не найти). Диагностика битого материала этим же обходом: TextureSample с `texture=None` = ошибка компиляции = дефолт-заглушка на меше.
**Статус: ПРИНЯТО и в основном РЕАЛИЗОВАНО (2026-07-02).** Пруф: git `0f7e612` (origin/feature/stage-c-village-reorg). НЕ ПРОВЕРЕНО: финальное подключение WPO Ринатом + сохранение уровня (MCP отвалился к концу сессии) — приёмка/докрутка Рината в PIE.
**Дозакрыто вечером 07-02:** ветер принят вживую, этап C целиком закрыт и влит в master `fb8a09f` (петля квестов на `L_World_C` PIE-пройдена Ринатом; сборка `BUILD_EXIT=0`).

## ADR-042 — ContrarySurvivor: баланс и старт брони для этапа E (Ринат, 2026-07-11)
**Контекст (реальное состояние кода, проверено 07-11).** Игрок при старте автоматически одевался в старую броню `_01` с суммарной защитой 0.50 — выше третьего тира (0.48), что ломало прогрессию. Вся броня Т1-Т3 лежала в магазине по тестовой цене 5 монет. Одежда Т0 (`SK_Cloth_T0_*`) существует в проекте, но не была никуда подключена (ноль ссылок в ассетах и в коде).
**Решения (Ринат, 2026-07-11).**
1. **Игрок начинает совсем без брони, с нулевой защитой** — каждый удар проходит в полную силу. Первая задача новичка — накопить монеты и купить первый комплект. Автонадевание брони `_01` при старте убирается. Визуальный стартовый облик игрока — одежда Т0, поставленная базовыми мешами в слоты тела Blueprint игрока: это не предмет, её нельзя снять или продать, и защиты она не даёт. Белого манекена в игре не остаётся: при снятии любой брони код возвращает базовый меш слота, то есть одежду Т0.
2. **Три ступени покупной брони.** Первый тир — самый дешёвый и берётся быстро: примерно по 50 монет за слот, полный комплект даёт около 15 процентов защиты. Второй тир — примерно по 120 монет за слот, комплект поднимает защиту до 30 процентов. Третий тир — самый дорогой, примерно по 250 монет за слот, полный набор даёт 48 процентов — это долгосрочная цель, к которой игрок идёт большую часть игры. Числа защиты в коде уже совпадают с этими ступенями (0.05, 0.10 и 0.16 на слот) — их не менять; цены заменить с заглушки «5 монет». Все числа делаются настраиваемыми в редакторе.
3. **Старую броню `_01` как ассет НЕ удалять.** Из каталога торговца её позиции убрать (в коде они есть: «Head/Pants/Torso Armor» за 60/80/120 — `MasterTrader.cpp:216-218`). На будущее Ринат думает отдать её жителям деревни — записано в бэклог, сейчас не делать.
**Статус: ПРИНЯТО (Ринат, 2026-07-11). Реализация — этап E, старт только по команде Рината.**

## ADR-043 — ContrarySurvivor: отображение брони и защиты в инвентаре и магазине (Ринат, 2026-07-11)
**Решение (Ринат).** На этапе E делаем простой и дешёвый вариант отображения по образцу STALKER. В инвентаре — три слота брони (шлем, торс, штаны): в занятом слоте видна иконка надетого предмета, пустой слот явно читается как пустой. Рядом выводится общая защита игрока цифрой (например «Защита: 30%»), и она сразу пересчитывается при надевании и снятии брони. В магазине у каждого предмета брони показывается, сколько защиты он добавит, чтобы игрок видел ценность покупки заранее. Крутящуюся 3D-модель персонажа (как в Last Day on Earth) не делаем — дорого и не окупается. На будущее закладывается возможность плоского силуэта персонажа (paper-doll) с 2D-картинками надетой брони — делается позже и только при наличии сил. Все числа защиты и цены выносятся в настройки, редактируемые в редакторе без переделки кода (лёгкий вынос сейчас; полная система таблиц данных — этап J по плану).
**Факт по коду (проверено 07-11).** Слоты брони в Canvas-инвентаре уже наполовину есть (`ContrarySurvivorHUD.cpp:381-417`): три слота с текстовым названием надетого и кликом «снять». Дорабатываются иконки, цифра защиты, прибавка защиты в магазине и русские подписи. ## ADR-044 — ContrarySurvivor: этап F — крючок через диалог старосты + квест Q3 «шкуры для торговца», тексты без «вернуться и забрать» (Ринат, 2026-07-11)

## ADR-045 — ContrarySurvivor: единый лут-конфиг «по образцу STALKER» (концепт принят, реализация — этап J)

**Статус: концепт ПРИНЯТ (Ринат, 2026-07-17). Сейчас НЕ реализуем; подпункт добавлен в этап J плановой таблицы.**

## ADR-050 — ContrarySurvivor: интерфейсные тексты переводим на штатную локализацию UE (FText), русский — первым языком (Ринат, 2026-07-20)
**Контекст.** Ринат вписал русские подписи в дизайнере WBP_PlayerStats — в игре остались английские. Причина найдена по коду: `UPlayerStatsWidget::NativeTick` (PlayerStatsWidget.cpp, строки 31/40/49/59/71) каждый кадр перезаписывает кубики через SetText из FString-приставок (PlayerStatsWidget.h, строки 27-40). Замер по репозиторию: `FText::FromString` — 41 вызов, `FString::Printf` в UI/HUD — 72, `LOCTEXT` — 0, текстовых FString-свойств — 86, папки `Content/Localization` нет, культура в DefaultGame.ini не задана. **Проверено в движке (UE 5.5, не по памяти):** макросы `LOCTEXT`/`NSLOCTEXT` — `Engine/Source/Runtime/Core/Public/Internationalization/Internationalization.h`, строки 295/300; плагин Localization Dashboard — `Engine/Plugins/Editor/Localization`; смена языка — `UKismetInternationalizationLibrary::SetCurrentLanguage` (+ `GetLocalizedCultures`), доступна из Blueprint.
**Решение.** Все видимые игроку тексты переводятся на `FText`: литералы в C++ — через `LOCTEXT` с namespace; настраиваемые надписи — `UPROPERTY(EditAnywhere) FText`; склейка — `FText::Format` с ИМЕНОВАННЫМИ подстановками (порядок слов в языках разный), не `FString::Printf`; числа — `FText::AsNumber`. Сборка переводов — штатным Localization Dashboard (.po для переводчика → .locres).
**Разделение подписей и значений (решение Рината «Разделять», 2026-07-20).** Статичная подпись и меняющееся значение — РАЗНЫЕ кубики: подпись («Здоровье») — обычный TextBlock в дизайнере, код её НЕ трогает и НЕ биндит (нулевая связанность, Ринат правит текст и стиль сам); код пишет только значение («80/100»). Цель — увести максимум слов из кода в дизайнер, под контроль Рината.
**Порядок работ (причинный, обязателен).** Сначала архитектура на FText, ПОТОМ русские тексты — одним проходом. Обратный порядок = та же работа дважды (русификация Уровня 1 из ADR-049 исполняется ВНУТРИ этого перевода, а не до него).
**Этапы.** (1) PlayerStatsWidget — эталонный образец нового паттерна, на нём же проверяется вид в игре. (2) Остальные панели UI/HUD по образцу. (3) Включение Localization Dashboard, первый реальный gather, культура ru по умолчанию — работа unreal-operator, требует редактора.
**Риски.** (а) Смена типа свойства FString→FText, ОЖИДАНИЕ (не проверено): ранее сохранённые в Blueprint значения сбросятся на новые дефолты — стилизацию (шрифты/цвета/раскладка) НЕ затрагивает, тексты сверить после сборки. (б) Сборка C++ требует ЗАКРЫТОГО редактора — пока Ринат стилизует панели, cpp только пишет код; сборка по его команде после сохранения. (в) Автоматический сбор FText из ассетов — стандартное поведение движка, но в НАШЕМ проекте gather ни разу не запускался → подтвердить первым реальным прогоном (этап 3), до того считать ожиданием.
**Ветка:** feature/localization от feature/umg-hud (161a3cc). **Статус: ПРИНЯТО (Ринат, 2026-07-20).**

## ADR-053 — ContrarySurvivor: Build 1.1 — боевая обратная связь и анимационный конвейер (2026-07-28)
**План Рината (Build 1.1), 5 пунктов дословно:** (1) «кнопка бега горела синим цветом и пульсировала, если включен режим бега»; (2) «человеческие персонажи, в том числе игрок и бандиты при стрельбе соответственно целились в противника»; (3) «при применении холодного оружия (ножа) — анимация удара размашистого (в будущем будем использовать эту анимацию и с другим холодным оружием)»; (4) вопрос «в каком WBP настраивать размер и внешний вид маркеров» — ОТВЕТ ФАКТОМ: маркеры не в WBP, их рисует HUD, настройки в BP_ContrarySurvivorHUD, категории HUD|TargetMarker, HUD|NPCMarker, HUD|QuestMarker; (5) «подсвечивать сектор в 100 градусов перед игроком... в этом же секторе должен наноситься урон».

**Принятые решения (game-lead, Рината не дёргал — инженерия):**
1. **Сектор ножа: подсветка обязана брать угол и дальность ИЗ ОРУЖИЯ** (геттеры MeleeSectorHalfAngleDeg/MeleeRange), а не иметь свои числа — «что видишь, то и бьёшь». Материал M_MeleeSector + MI_MeleeSectorSoft (Deferred Decal/Translucent, 228 инструкций, без текстур; контракт скаляров SectorHalfAngleRad/InnerRadiusFrac/Opacity/EdgeSoftness + вектор SectorColor). 2. **Мгновенный доворот при ударе ножом ОТМЕНЁН** в пользу плавного (StartAimTurnTo, как при стрельбе). Основание — дословная формулировка Рината «в ЭТОМ ЖЕ секторе»: рывок бил вне подсвеченного сектора. Возврат к прежнему поведению — галочкой bMeleeSnapToTarget «Мгновенный доворот при ударе» (дефолт выключен). Цена, названная честно: первый взмах мимо цели промахнётся, корпус доедет за ~0.3 с при кулдауне 1 с.
3. **Скелеты-дубли НЕ сводим** (32 меша на одном, ABP и голова игрока на другом) — вместо этого взаимная CompatibleSkeletons (коммит 307bc76). Сведение и переезд боевого скелета из папки TestContentAndCode/PreProduction — в бэклог.
4. **Правка графа AnimBP — только редакторным кодом C++,** не кликами: коммандлет PatchAnimBp (режимы основной/-verify/-dump/-aim) по образцу GenerateWbp. Имя монтажа НЕ привязано к ножу (AM_MeleeSlash) — требование Рината про другое холодное оружие.
6. **Бандиты бьют и стреляют МИМО классов оружия** (ИИ наносит урон напрямую, оружие только для вспышки и звука) — поэтому крючки анимаций в ЧЕТЫРЁХ местах, иначе у бандитов анимации не было бы. ## ADR-058 — ContrarySurvivor: ревизия перед первой публикацией (2026-08-05, запрос издателя)

**Контекст.** Издатель запросил честную картину проекта перед тихим валидационным запуском на RuStore (промпт `E:\Publisher\Publusher\Promt-revizia-dlya-gamelead-2026-08-05-v3.md`, версия 3). Отчёт — `reports/2026-08-05-audit/otchet.md`, копия у издателя.

Журнал игры и файл сохранения лежат в `/sdcard/Android/data/<пакет>/files/UnrealGame/ContrarySurvivor/ContrarySurvivor/Saved/`.

**Установленные причины (каждая с файлом и строками, проверены лидом лично):**
1. **Бандиты не падают (замечание Рината 1) и не видно сектор ножа (замечание 7) — ОДИН корень: третий и четвёртый случай болезни ADR-057.** `Anim_Death_Humanoid` (мягкая ссылка `MasterHumanoidCharacter.h:100`) и `MI_MeleeSectorSoft`/`M_MeleeSector` (мягкая ссылка `MeleeSectorIndicatorComponent.h:62`) в пакет НЕ попали. Пруф: в `Manifest_UFSFiles_Android.txt` есть `Anim_AimPistol_Humanoid`, `Anim_Run/Walk_HumanoidCharacter`, все волчьи включая `Anim_Wolf_Death` и десятки материалов, а этих трёх ассетов нет вовсе (на диске лежат). Следствие: анимация смерти не работает и у ИГРОКА тоже. Лечение — папки `/Game/Characters/Shared/Humanoid` и `/Game/Materials` в `+DirectoriesToAlwaysCook`. **Причина отсутствия сектора НА ПК не установлена** — там ассет на месте.
2. **Магазин, «не работает ползунок количества» (замечание 2).** При ПОКУПКЕ работает (проверено живьём: «3 из 4», «Итого: 15»). Ломается ПРОДАЖА: `ShopScreenWidget.cpp:355` — для всего, кроме патронов, `TransactionQtyMax = 1` жёстко. Стаки введены волной 1.2.1 (ADR-055), ветку продажи под них не обновили.
3. **Нет золотой кнопки «продать дороже» (замечание 3) — НЕ баг кнопки.** Все пять условий реализованы (`ShopScreenWidget.cpp:473-517`): порог 360 с (`PlayerCharacter.h:379`), минимум сделки 50 (`ShopScreenWidget.h:151`), готовность ролика, лимит 4/сутки, задержка 180 с, бонус ×1.5. Срабатывает «сумма < 50», и это ПРЯМОЕ следствие п.2: продать партию нельзя, значит сделка почти всегда дешевле порога. Чинить п.2, потом проверять кнопку.
4. **Интро при каждом запуске и старт в начальной точке (замечание 9).** Сохранение ПИШЕТСЯ (`SaveGame -> slot 'ContrarySave' : OK`, файл на телефоне обновляется), но при старте НЕ ЧИТАЕТСЯ — загрузка вызывается только при возрождении после смерти (`PlayerCharacter.cpp:1960`), в BeginPlay её нет по замыслу авторов (`PlayerCharacter.h:326-327`). Это не поломка, а непостроенная часть: каждый запуск = новая игра.
5. **Аналитика не работает вообще.** Журнал телефона: `Analytics: keys not found in 'E:/game-dev-team/keys' - analytics silently disabled` — путь ведёт на рабочий компьютер, в сборке ключей нет. Ни одного события не уходит.
6. **Реклама РАБОТАЕТ на живом Android (снято с этого статуса «НЕ ПРОВЕРЕНО»).** Полный цикл на телефоне: `init (consent=yes)` → `sdk initialized (version 8.2.0)` → `loaded` → `save-backpack button clicked` → `show requested (death_backpack)` → `shown` → `rewarded - 1 Reward` → `finished (completed), reward=yes`. Ролик виден глазами, награда выдана, возрождение у костра прошло. **Плагин — рекламная сеть ЯНДЕКСА 8.2.0, а не VK/myTarget из РИ-4** (расхождение с журналом издателя, требует отдельного решения). Идентификатор ДЕМОНСТРАЦИОННЫЙ (`YandexAdService.h:56`, `demo-rewarded-yandex`), денег показы не приносят: нужен кабинет + боевой блок + статус для выплат.
7. **Производительность на минимальном устройстве ниже порога РИ-21.** Замер по счётчику на экране: поле 25-28, деревня 19-24, инвентарь 22, диалог и магазин 19-20 кадров при цели ≥30. Отдельно: журнал телефона ругается `M_VColor missing bUsedWithInstancedStaticMeshes=True` — часть массово размноженных объектов рисуется движковым материалом.
8. **Чего нет вообще:** главное меню, настройки, экран согласия на данные и политика (риск модерации RuStore, РИ-26), три выхода в Telegram (РИ-27), карточка конца контента и полоска прогресса накопления (РИ-28).
9. **Мелочи с экрана телефона:** подписи клавиш компьютера («Закрыть (Tab)», «Enter / Пробел — возродиться»); подписи брони в магазине не влезают и налезают на соседний ряд; смерть от жажды подписана «Убийца Неизвестно»; иконка оружия на боевом экране снята под углом сверху (в инвентаре и магазине иконки нормальные).
10. **Дыра в экономике (найдена по ходу):** вода покупается за 5 и продаётся за 6 — бесконечные деньги на одном торговце.

**Сделано сразу:** реплика старосты «дай срок» → «дай мне время» (`ElderNPC.h:218`, замечание 5 издателя).

**Открытая развилка Рината:** патроны на старте (замечание 6). Предложение лида — не выдавать огнестрел вовсе (только нож), пистолет купить у торговца за 150 монет: это же даёт «видимую цель накопления» из РИ-28. Запасной вариант — оставить пистолет, урезав патроны с 48 до 6. Ждёт решения владельца.

**Статус: отчёт отдан издателю, правки НЕ начаты.** Порядок работ — по трём корзинам из отчёта, первыми: загрузка сохранения при старте, аналитика с настоящими ключами, предел количества при продаже, возврат потерянных ассетов в пакет.

**Дополнение ADR-058 (решения того же дня, 2026-08-05, после ответа Рината).**
1. **Старт без огнестрела — УТВЕРЖДЕНО Ринатом** (дословно: «согласен»). Новому игроку выдаётся только нож, пистолет покупается у торговца за 150 монет. Довод: первое задание — охота на волков (ближний бой читается лучше), пистолет становится первой целью накопления, то есть «видимой целью» из РИ-28. Дополнение Рината дословно: «староста должен в первом диалоге как-то намекнуть что пистолет игрок может накопить денег и купить пистолет у торговца» — намёк добавляется в скриптовое вступление (`ElderNPC.cpp:112-134`), формулировку утверждает лид.

При 15 десять шкур = 150 = цена пистолета, цепочка «охота → деньги → оружие» замыкается. Категорию предмета (квестовый) не меняем, правится только цена.
3. **Дыра в экономике закрывается** (Ринат: «Дыру в экономике устраняй»). Сейчас вода покупается за 5 и продаётся за 6 (проверено лидом лично на телефоне) — бесконечные деньги. Правило: цена продажи строго ниже цены покупки; остальные товары проверяются на такой же перекос.
4. Задачи розданы: cpp — предел количества при продаже, экономика, цена шкуры, старт без пистолета, намёк старосты; unreal — возврат ассетов в пакет (папка `/Game/Characters/Shared/Humanoid` в `DirectoriesToAlwaysCook`; материал сектора назначить прямо в `BP_PlayerCharacter`, а не тащить всю папку Materials), флаг `bUsedWithInstancedStaticMeshes` у `M_VColor`, сбор фактов по кадрам.

**Дополнение ADR-058 (факты помощников, дописано после первой версии отчёта).**
- **Собранный APK непубликационный:** режим `Development` + `android:debuggable=true` в манифесте + отладочная служба удалённого доступа к файлам. В магазин не примут, нужен Shipping.

## ADR-061 — ContrarySurvivor: петля смерти на возрождении без костра (2026-08-06/07, живой прогон дистрибуционного пака)

**Находка (оператор, кадры `Screenshots/phone-dist-03..05*.png`, просмотрены лидом).** Игрок, погибший ДО активации первого костра, возрождается в чистом поле на стартовой точке, где дежурит убивший его волк: четыре смерти подряд за 9/4/2/2 секунды, монеты 50→3. Хуже того, пере-сохранение после возрождения записывает точку поля в сейв как «точку костра» — петля закрепляется в файле сохранения; разрывается только перезапуском приложения (волки расставляются заново). Текст экрана смерти «Возрождение у костра в деревне» — статичная строка, реальность не проверяет.

**Корень (cpp, подтверждён кодом):** `Respawn()` грузит сейв и телепортирует на сохранённую точку (`PlayerCharacter.cpp:2188` → `ApplySaveData:1810`); позицию пишут только костёр (`Campfire.cpp:88`) и пере-сохранение после возрождения (`PlayerCharacter.cpp:2005`). Нет сейва → запасной телепорт на стартовую точку игры (`PlayerCharacter.cpp:2199`). GDD §7.8 определяет «возрождение на последнем костре», случай «костра ещё не было» не определён.

**Решение лида (вариант 1+3, в рамках обещания экрана смерти и GDD):**
1. Нет сейва или в сейве нет валидной точки → возрождение у деревенского костра (в уровне он один); поиск костра — устойчиво по классу, не по имени экземпляра.
2. Лечение испорченных сейвов: при возрождении после смерти, если сохранённая точка не рядом с костром (радиус — настраиваемый параметр EditAnywhere), — возрождать у деревенского костра. «Продолжить» не трогаем: там позиция из сейва легитимна.
3. Осознанный минус: погибший во время интро-прогулки очнётся сразу в деревне, остаток прогулки пропустится. Принято — безопасность новичка важнее.

**Тем же расследованием, баг 2:** после «Продолжить» в интро-этапе не восстанавливаются баннер задачи и стрелка-указатель (их выставляет только интро-последовательность, которая при «Продолжить» сознательно не запускается — Б3; состояние интро в сейв не пишется). Починка: после загрузки с пустым журналом квестов восстановить баннер/стрелку и перевести интро-машину в фазу «управление у игрока» — дальше работает штатный код перехода к деревне. Ветка `fix/respawn-at-campfire`, работы идут.

**Поправка к п.2 (2026-08-08, ночь; решение лида по расследованию cpp-2, жалоба Рината «игрок стартует не с PlayerStart»).** Пункт «"Продолжить" не трогаем: там позиция из сейва легитимна» ОТМЕНЁН: испорченную петлёй смерти точку слот доносил до игрока именно через «Продолжить» (подтверждено живым логом 22:39 07.08: CONTINUE mid-intro → игрок в поле → смерть от бандита за 48 с). После фикса 08-06 позицию в слот пишут только автосейв костра и пере-сейв после смертельного возрождения (оба — у костра), поэтому точка дальше порога от ближайшего костра в слоте может быть ТОЛЬКО испорченной. Лечение перестановкой к костру теперь работает в обоих путях применения сейва (смерть И «Продолжить»); порог — прежний параметр RespawnNearCampfireRadius (EditAnywhere, 1000 см). Новая игра и первый запуск — строго PlayerStart (подтверждено дампом карты: PlayerStart один). Коммит `424c4a9`, тесты 77/77, включая 3 новых ContinueSpawn.

## ADR-063 — ContrarySurvivor: решения издателя 08-08 вечер — баланс выживания, единый поток огнестрела, порог рекламы; отмена пункта про AppMetrica (2026-08-08)

**4. AppMetrica — пункт ОТМЕНЁН, текст согласия НЕ меняем.** Моё утверждение издателю «AppMetrica в сборке физически нет» оказалось ОШИБКОЙ неполной проверки (искал по плагинам и грепу имён): AppMetrica приезжает в пакет как обязательная зависимость рекламного SDK Яндекса, версия прибита в `Plugins/YandexAds/Source/YandexAds/YandexAds_UPL.xml:58` (`io.appmetrica.analytics:analytics:8.3.0`, сверено по кэшу Gradle 02.08). Текст согласия с ТРЕМЯ сборщиками (Яндекс, AppMetrica, GameAnalytics) — правильный, остаётся; автотест ConsentAutomationTests, требующий AppMetrica в тексте, — тоже. Издателю отправлена поправка, его текст политики должен включать все три.

**Кнопка рекламы при незагруженном ролике** — остаётся скрытой (подтверждение издателя, поведение уже такое). Причина недоставки ролика в живой сессии Б2 установлена: SDK вообще не инициализировался в повторных сессиях (дефект «реклама только в первой сессии», корень в DataConsentSubsystem — фикс уже в волне у cpp).

## ADR-064 — ContrarySurvivor: волна главного меню, подходы 2 и 3 — решения лида по развилкам, которых не было в спеке (2026-08-09)

Волна `feature/main-menu-0808` закрыта со стороны кода (HEAD `a86e70d`, 14 коммитов от master `d7291fb`). Ниже — только решения, которых НЕТ в `glavnoe-menu-spec.md` и в ADR-062/063: их пришлось принимать по ходу, и они не должны потеряться.

**1. Класс настроек — наследник `UGameUserSettings`, не своя подсистема** (решение cpp, принято мной). Сохранение между запусками, применение без перезапуска, пресет качества, масштаб разрешения и предел кадров — готовые механизмы движка; свой класс подставляется строкой `GameUserSettingsClassName` в `Config/DefaultEngine.ini`. Цена: объект живёт в движке и не знает про игровой мир, поэтому громкость играющего звука и прозрачность экранных кнопок применяет контроллер. Отдельный автотест проверяет, что движок действительно создаёт наш класс, — он ловит потерю строки в конфиге, без которой весь экран работал бы вхолостую.

**2. Порядок применения: пресет ПЕРЕД масштабом разрешения.** Команда движка «поставить общий уровень качества» заодно перетирает масштаб. Порядок закреплён кодом, комментарием и тестом.

**3. Фиксированное снижение разрешения в профилях устройств УБРАНО** (`+CVars=r.MobileContentScaleFactor=0.8` в `Android_High` и `Android_Unknown_Vulkan`). Причина: два конкурирующих источника — профиль устройства резал бы картинку поверх выбора игрока. Возвращать нельзя; в файле оставлено пояснение.

**4. Автовыбор пресета — по памяти и ядрам, без замера производительности.** Три гигабайта памяти и меньше ЛИБО четыре ядра и меньше — низкое; восемь и больше того и другого — высокое; между — среднее; молчащее устройство считается слабым. Встроенный замер движка не используем: он отъедает первые секунды после установки, а они самые дорогие. Пороги стартовые, уточняются по живым замерам.

**5. Вибрация привязана к двум событиям: урон игроку (короткий импульс) и смерть игрока (длиннее).** На взмах ножа, выстрел и попадание по врагу НЕ вешаем: игрок машет ножом постоянно, телефон тряс бы без остановки и сажал батарею. В диздоке про вибрацию есть только сам переключатель (`glavnoe-menu-spec.md:46`), поэтому решение моё, ощущения судит Ринат живьём. Сила и длительность обоих импульсов — редактируемые поля.

**6. Адрес Telegram — один.** Канал у Рината планируется один. Правило: свой `BugReportUrl` задан — идём по нему; пуст, а `CommunityUrl` задан — «Сообщить об ошибке» ведёт в чат сообщества и пункт виден; пусты обе строки — пункт спрятан. Отдельная строка остаётся дверью на будущее.

**7. Счётчик кадров: компиляционный запрет в релизной сборке СНЯТ с самого счётчика, требование издателя держится значением по умолчанию «выключен».** Основание — дословная формулировка утверждённой спеки: «Счётчик кадров — переключатель, по умолчанию ВЫКЛЮЧЕН. В релизе счётчик не виден, пока игрок сам его не включит». Отладочная строка с временами кадра осталась под компиляционным запретом и в релизе отсутствует. Это заметное изменение поведения релиза; если издатель имел в виду «счётчика в релизе не должно быть ни при каких условиях» — запрет вернуть.

**8. «Прогресс не сохранён» определяется по ЗАРАБОТАННОМУ, а не по всему состоянию.** В снимок при каждом сохранении и при загрузке через «Продолжить» входят: деньги, число предметов в рюкзаке штуками с учётом стаков, число квестов в журнале и число сданных. Здоровье, голод, жажда и координаты НЕ входят: они ползут сами каждую секунду, и вопрос «выйти без сохранения?» выскакивал бы всегда, а значит перестал бы что-либо значить. Снимка ещё нет (в сессии не сохранялись и не загружались) — спрашиваем: лишний вопрос стоит одного касания, молчание стоит игроку прохождения.

**9. Возврат в меню из паузы НЕ перезагружает уровень** — открывает меню поверх того же мира, дальше игрок выбирает «Продолжить» или «Новую игру», как при запуске. Отдельная перезагрузка — лишние секунды чёрного экрана на слабом телефоне. НЕ ПРОВЕРЕНО живьём: не остаётся ли в мире что-то «от прошлой жизни» (например разложенный лут) — проверить на телефоне.

**10. Живые ассеты окон вводились ТРЕМЯ разными режимами генератора, по степени риска для ручной стилизации Рината** (важный рабочий приём, повторять): экран меню — точечная пересборка `-rebuild -asset=WBP_StartScreen` (правок владельца в нём не было, git-история — единственный коммит генерации); экран настроек — обычная генерация без `-force`, которая создаёт только отсутствующие ассеты и пропускает все существующие; панель паузы — точечное дополнение `-augment`, идемпотентное, потому что панель уже стилизована владельцем и гнать по ней пересборку ради одной кнопки — риск без нужды. Полный `-force` по-прежнему НЕ гнать никогда.

**11. Съёмка кадров экранных окон на компьютере НЕ РАБОТАЕТ прежним способом и отложена.** Скрипт `shoot-game-frames.ps1` снимает вид с камеры игрока после загрузки мира; меню живёт до мира. Моя попытка снять окно игры захватом экрана провалилась дважды: захватилось чужое окно и щелчок мыши ушёл в него, а игра была убита раньше времени — она компилировала шейдеры и до загрузки уровня не дошла. Скрипт удалён, чтобы не остался ловушкой. Рабочий путь на будущее, если понадобится: консольная команда `shot showui filename=<абсолютный путь> -nosuffix` (сверено с исходником движка `GameViewportClient.cpp:3192,3926-3939` — именно `showui` включает съёмку экранных окон), а режим ввода при открытом меню — `FInputModeGameAndUI`, то есть отладочные привязки клавиш до игры доходят. Сейчас проще и честнее: смотреть на телефоне.

**Дополнение ADR-064 (12) — проверка окон не отличала целый экран от сломанного; заказана печать геометрии (2026-08-09, разбор qa).** Режим `-verify` печатает про каждый виджет только имя и класс (`GenerateWbpCommandlet.cpp:5409-5410`); ни один из девяти режимов коммандлета не печатает позицию, размер, якоря и выравнивание. Поэтому экран с подложкой, сжатой с 560 до 320, и кнопками на позициях -100 и -30 получил такой же зелёный штамп, как идеальный, — брак прошёл мерж-гейт и уехал на телефон к Ринату. Решения: (а) в `-verify` печатать геометрию канвас-слотов и РУГАТЬСЯ ОШИБКОЙ на пересечение прямоугольников видимых элементов, выход за родительскую подложку и нулевой размер, с явным списком честных исключений (штатно свёрнутые ряды, фоновые слои, намеренные наложения); задача поставлена cpp следом за переделкой меню; (б) правило qa: по каждому новому или пересобранному окну писать в вердикте АДРЕСНУЮ строку «раскладка headless не проверена, нужен живой осмотр», а не общий раздел про границы; (в) порядок перед слиянием визуальных волн: переделка → прогон генератора → пакет → ЖИВОЙ ОСМОТР РИНАТА → повторный гейт qa (полные тесты, не выборочные) → маркер и слияние. Живой осмотр идёт ПЕРЕД гейтом: нет смысла гонять полную проверку по раскладке, которую Ринат может завернуть.

## ADR-065 — ContrarySurvivor: награда за первое задание поднята до 200, первое оружие становится покупкой игрока (Ринат, 2026-08-09)

**Замысел Рината (дословно):** «игрок стартует с ножом, а первый пистолет покупает сам — на деньги, которые староста платит за первое задание. Награда должна покрывать не только пистолет, но и подлечиться с припасами, иначе игрок уйдёт в лес голым и умрёт на ровном месте… Мне важен эффект: первое оружие — решение игрока, а не подарок.»

**Числа взяты из РЕАЛЬНОГО прайса торговца** (`MasterTrader.cpp:294-315`, прочитан перед расчётом, не по памяти): пистолет 150, нож 40, бинт 12, консервы 12, вода 5, патрон 2 за штуку. Выкуп шкуры волка — 15 (`MasterTrader.cpp:54`, особая цена). Стартовые деньги игрока 50 (`PlayerCharacter.h:330`). Награда за кв.1 была 150, за кв.2 — 250 (`ElderNPC.cpp:66,94`).

**РЕШЕНИЕ: награда за первое задание 150 → 200. Цену пистолета НЕ трогаем** — она укладывается в логику, двигать её незачем.

**Расчёт покупательной способности у торговца после сдачи кв.1:**
- Стартовые 50 монет к этому моменту ЦЕЛЫ. Это не допущение, а следствие ADR-063: жажда доходит до критики примерно за 21 минуту, а урон от истощения приглушён до сдачи первого квеста — покупать еду и воду до похода к старосте игроку просто незачем.
- Четвёртая шкура (волков в демке 4, квест забирает 3) продаётся за 15 — необязательный бонус.
- Итого на руках 250 монет, при продаже лишней шкуры 265.

**Что на это покупается:** пистолет 150 → остаётся 100 свободных. Разумный набор: бинт 12 + консервы 12 + вода 5 + 20 патронов 40 = 69, **остаток 31 монета**. При продаже лишней шкуры остаток 46.

**Почему именно 200, а не 250 «чтобы хватило на всё».** Сто свободных монет — это настоящая развилка: игрок выбирает между полусотней патронов и запасом еды с бинтами. Если награда покрывает всё разом, выбора нет, а Ринат просил ровно обратного — чтобы первое оружие было решением. Тесно, но достаточно: без пистолета игрок уйти не может, а как именно снарядиться — уже его дело.

**Награду за кв.2 (250) НЕ меняем.** Разрыв 200/250 выглядит небольшим для заметно более тяжёлого задания, но кв.2 — последний квест демки: деньги после него тратить уже негде, и раздувать их незачем. Если демка вырастет — вернуться к числу.

**Подсказка от старосты при выдаче награды.** Добавляем намёк на торговца и оружие голосом персонажа, не инструкцией и не подсветкой. Смысл: «заработал; загляни к торговцу под навесом; с ножом на волка — дело молодое, а с железом и подальше уйти можно; про припасы не забудь». Техническая тонкость: поле `DialogueCompletedText` (`ElderNPC.h:140`) общее для ВСЕХ квестов, поэтому подсказка в него не пишется — иначе она повторится при сдаче кв.2. Заводится отдельный текст только для первой сдачи.

**НЕ ПРОВЕРЕНО на момент записи:** живой проход «сдал квест → дошёл до торговца → купил» с замером остатка и времени пути. Ринат просил проверить руками — проверка после сборки.

## ADR-066 — ContrarySurvivor: разбор вечерней волны 08-09 (полосы состояния, стик, вид меню, размер настроек)

Волна по итогам живого осмотра Ринатом сборки `c1dd5d7`. Ниже — решения и уроки, которых нет в спеке меню и в ADR-062/063/064.

**1. УРОК ДВИЖКА, стоивший полного отказа игрового интерфейса: виджет, который делает невидимым САМ СЕБЯ, теряет ежекадровый вызов навсегда.** Днём панель со здоровьем, голодом и жаждой была научена прятаться, пока открыто главное меню, — и пряталась она командой «стать невидимой» на самой себе. В движке 5.5 ежекадровый вызов приходит виджету только пока его рисуют, поэтому развернуться обратно панель уже не могла: после закрытия меню игрок остался вообще без полос и без денег. Подтверждение не по рассуждению, а по журналу живой сессии с телефона (`context/game-lead/logs/phone-0809-evening.log`): диагностическая строка панели напечаталась ровно один раз, в нулевом кадре до открытия меню, а дальше игрок провёл в мире ещё около 280 кадров без единой записи. Лечение: панель прячет только своё СОДЕРЖИМОЕ и остаётся живой, а решение «показать или скрыть» принимает игровой интерфейс снаружи. Правило на будущее: любое окно, умеющее прятаться само, прячет содержимое, а не себя. В проекте эта ловушка уже была описана у трекера задания и подсказки действия (база `USelfHidingWidget`, баг 07-18) — то есть команда наступила на свои же грабли второй раз, поэтому правило вынесено в ADR.

**2. Размер элемента под палец задан числом, а не на глаз: порог 9 мм.** Пересчёт для телефона Рината (720 на 1600 точек, плотность 320 точек на дюйм, масштаб интерфейса 0.666): 9 мм = 113 настоящих точек = 170 точек интерфейса. Принято 172 с запасом; зазор между соседними элементами — не меньше половины высоты элемента, чтобы промах уходил в пустоту. Порог держится автотестом, который перебирает ВСЕ элементы экрана настроек, и проверкой по самому файлу окна — она ловит случай «код поправили, а окно не пересобрали». Первый же прогон этой проверки поймал настоящий брак: кнопки выросли, а пять ползунков остались высотой 44 — возвращено в работу.

**3. Прокрутка в настройках — вынужденная, решение моё, ждёт приговора Рината.** Окно настроек увеличено с 520 на 620 до 1500 на 960 точек, то есть почти во весь экран; больше нельзя — выше экрана окна не бывает. Девятнадцать пунктов при высоте строки 172 в эту высоту не помещаются (влезает шесть с половиной), поэтому настройки стали одним столбиком с прокруткой пальцем. Ринат просил именно «увеличить окно, кнопки и расстояния» и прокрутку не заказывал; альтернатива — разбить настройки на две-три страницы с переключением. Решает он после живого осмотра.

**4. Вид главного меню приведён к макету** `concept-art/menu-mockups/menu-background-A-check.png`: подложка вокруг столбика кнопок и холодная синевато-серая рамка убраны, кнопки крупные тёплые коричневые с тонкой рамкой, «Продолжить» выделена оранжевой заливкой, подпись на ней тёмная (по макету, а не белая). Заголовок «С возвращением» и строка про найденное сохранение из обычного меню убраны, но НЕ удалены: они показываются в переспросе «начать заново и стереть прогресс?», иначе игрок увидел бы там две безымянные кнопки.

**5. Переезд окон на живые файлы — по факту закончен, проверено прогоном, а не на слово.** `-verify` подтвердил: все 13 слотов окон на игровом интерфейсе заполнены живыми файлами и ни один не пустует (магазин, разговор, рюкзак, смерть, полосы состояния, трекер задания, подсказка действия, обыск трупа, ежедневная награда, согласие, подсказка обучения, значок хромоты, показ рекламы), плюс главное меню, настройки, вступление и пауза на контроллере. Без своего файла остались два элемента: служебный отладочный список сообщений (игроку не показывается, в релизе отсутствует — переводить не будем) и строка задачи вступления вверху по центру — она поставлена в работу.

**6. Стик поднят: отступ снизу приравнен к отступу слева** (240 точек эталонного экрана вместо 160), по прямой просьбе Рината. Требование держится тестом, а не комментарием.

## ADR-067 — ContrarySurvivor: ночная волна 08-09 (звук, баланс, адреса, отложенный переезд запуска)

**1. Музыка в паузе не играла, потому что трека не было в пакете.** Ссылка на звук мягкая (тянется в момент открытия паузы), а упаковщик мягкие ссылки не видит: в собранном пакете в `Content/Audio` лежала только папка `Demo`, папки `Music` не было вовсе, игра честно писала в журнал «трек паузы не загрузился». Лечение — папка `/Game/Audio/Music` добавлена в обязательную упаковку (`Config/DefaultGame.ini`), после чего папка `Music` в пакете подтверждена глазами. Жёсткую ссылку сознательно НЕ ставим (довод cpp принят): она привязала бы трек к классу навсегда и лишила Рината возможности подменить музыку, а от той же беды не спасла бы — достаточно положить новый трек в неучтённую папку. Правило на будущее: любой ассет, который тянется только мягкой ссылкой, обязан быть в списке обязательной упаковки.

**2. Адрес Telegram обрезался движком до «https:».** Причина не в коде игры, а в чтении настроек: незакавыченный двойной слэш считается началом комментария — исходник движка 5.5, `ConfigCacheIni.cpp:1776-1780`, дословно «it contains unquoted '//' (interpreted as a comment when importing)». Правило: ЛЮБОЙ адрес в файлах настроек пишется в кавычках. Закреплено тестом, который читает все четыре адреса игры теми же методами, что и игра, и требует целостности («https://» + узел с точкой), поэтому обрубок проверку не проходит.

**3. Баланс по просьбе Рината: нож 35 → 40, укус волка 12 → 10.** Развилки промежуточных значений у ножа НЕТ: при здоровье волка 40 и бандита 80 любое значение от 36 до 39 не меняет ни одного исхода боя, а 40 срезает по удару сразу обоим. Выбрано 40 — иначе просьба не выполняется вовсе; цена решения названа Ринату прямо: волк падает с одного удара, бандит с двух вместо трёх. Укус снижен ровно до 10, то есть до базового урона обычного врага — зверь перестал кусать больнее вооружённого бандита. Итог: под одним волком игрок живёт 10 укусов вместо 9. Оба числа лежат каждое в одном месте и правятся одним значением. Старый тест, пинивший точное число урона, ослаблен намеренно: Ринат будет крутить баланс сам, а тест, падающий на каждой его правке, приводит к тому, что тесты перестают читать.

**4. Окна, отданные владельцу, генератор больше не пересобирает.** У экрана настроек и меню паузы стоит признак «принадлежит владельцу»: точечная пересборка их пропускает, принудительная перезапись тоже, дополнить можно только режимом `-augment`, создать с нуля — если файла нет. Проверка по таким окнам смотрит ТОЛЬКО состав (все ли элементы на месте, не замкнут ли элемент в редакторе) и не придирается к положению и размеру. Причина: дважды за день перенос значений владельца молча портил окна — сначала уехала раскладка меню, потом вернулся мелкий шрифт в настройках. Ошибочное требование «каждый элемент обязан быть переменной» снято: сверено с исходником движка, признак читается только компилятором окон (`WidgetBlueprintCompiler.cpp:567`) и в дизайнере не встречается вовсе, то есть на правку мышкой не влияет; вместо него проверяется то, что действительно мешает человеку — замок на элементе.

**5. Требование Рината к запуску игры (переезд отложен, код НЕ начат).** Дословно: первый запуск после установки — сразу в мир и играть; любой следующий — главное меню, и мир грузится ТОЛЬКО после «Продолжить» или «Новая игра». Декоративную сцену под меню делать запретил, поэтому заведён пустой технический уровень `L_Boot` (13 650 байт, два актёра, ноль связей с игровым содержимым). Работа отложена сознательно: она трогает путь «Продолжить», её нельзя дробить (до конца переезда сборка хуже нынешней) и нельзя сдать без живого осмотра. Две ловушки, найденные разведкой и обязательные к учёту: режим игры новому уровню назначается одной строкой в настройках по началу имени карты; признак «игра уже запускалась» не читается, а ставится в момент чтения, поэтому решение принимается ровно один раз на загрузочном уровне, а дальше в мир едет явное намерение — иначе первый запуск после установки тихо сломается и покажет меню поверх мира.

**Дополнение ADR-067 (6) — витринные кадры для магазина сняты, кадра открытого мира не будет (2026-08-09 ночь).** Семь кадров ровно 1920 на 1080 лежат в `reports/store-screenshots/` (коммит `345f3b2`), четыре ключевых я просмотрел лично. Способ, который РАБОТАЕТ и который надо повторять: игра поднимается как игра (`-game -ResX=1920 -ResY=1080 -windowed`), кадр снимается встроенной командой снимка ВМЕСТЕ с экранными окнами — обычный «снимок высокого разрешения» не годится, он рисует мимо окон, а рюкзак и лавка у нас именно окна. Мобильный вид на компьютере получается сам, потому что слой пальцевых кнопок включён; отдельный мобильный предпросмотр не нужен. Ловушка: игра игнорирует размер окна из строки запуска и подставляет своё сохранённое разрешение, поэтому файл настроек временно подменяется и возвращается. Организационно: запуск игры оператору запрещён системой прав, поэтому игру поднимает game-lead, а оператор снимает в уже живом окне. **Кадр открытого мира снимать отказались осознанно:** камера в игре смотрит строго сверху вниз и дали не показывает в принципе, а за деревней ровное пустое поле без леса, дороги и строений — по правилу качества Рината («лучше пять хороших кадров, чем шесть, где один выдаёт самоделку») вместо него в наборе главное меню и разговор со старостой. Если кадр мира нужен, это отдельная работа: либо красивый уголок на карте, либо отдельная камера. Побочно замечен дефект, требующий проверки: вызванный волк забрался на крышу дома у лавки торговца — похоже на ошибку хождения врагов.

## ADR-068 — ContrarySurvivor: внешним видом рекламного ролика управлять нечем, менять его мы не будем (2026-08-11, поручение Рината от 08-09)

**Повод.** Ринат живьём пожаловался: у вознаграждаемого ролика мелкие счётчик секунд, стрелка и крестик закрытия, а рядом системная кнопка выхода — легко промахнуться. Поручение было дословно: «Ничего не трогай, но в следующей сессии на всякий случай изучи документацию яндекса на этот счёт».

**Как проверяли.** Документацию Яндекса открыть НЕ удалось: выхода в интернет в этой рабочей среде нет — мои собственные попытки обратиться к сайту заблокированы системой разрешений, у помощников инструментов веб-поиска и загрузки страниц в наборе не оказалось (проверено тремя разными подходами, все три отказ). Поэтому проверка велась по более надёжному источнику, чем справка, — по самому файлу библиотеки рекламы, который лежит на этой машине и попадает в нашу сборку: `C:\Users\pgr40\.gradle\caches\modules-2\files-2.1\com.yandex.android\mobileads\8.2.0\...\mobileads-8.2.0.aar` (7 923 526 байт) и адаптер посредника `mobileads-mytarget-5.45.3.3.aar`. Наличие или отсутствие настройки в поставляемой библиотеке — это факт, а не описание.

**1. Настроек внешнего вида ролика в библиотеке НЕТ (проверено лично).** У объекта ролика ровно три доступных действия — узнать сведения о рекламе, подписаться на события, показать. Я лично распечатал его состав: `javap -public com.yandex.mobile.ads.rewarded.RewardedAd` → `getAdInfo()`, `setAdEventListener(...)`, `show(Activity)`, и больше ничего. У заказа рекламы единственная настройка, влияющая на вид, — пожелание светлой или тёмной темы (значения ровно два: LIGHT и DARK), геометрии крестика и счётчика не касается. Классы настройки оформления в библиотеке есть, но для других форматов (лента, retail media), для вознаграждаемого ролика аналога нет — похоже, отсутствие намеренное.

**2. Почему крестик выглядит мелким (проверено лично по файлу размеров библиотеки).** Собственные размеры библиотеки: элемент крестика 60dp, внутренний отступ 18dp с каждой стороны, высота счётчика 24dp. То есть нажимаемая область у крестика крупная (60dp — на телефоне Рината это 120 точек экрана), а видимый рисунок примерно 24dp: он мелкий на вид, но палец попадает по гораздо большей зоне, чем кажется. Хорошая новость, тоже из файла библиотеки: при попытке закрыть ролик досрочно показывается вопрос «Закрыть рекламу?» с текстом «Если закрыть рекламу до окончания таймера, награда за просмотр не будет начислена» и кнопками «Закрыть» и «Досмотреть» — случайное касание награду не отнимает молча.

**3. Перекрывать размеры библиотеки своими — ЗАПРЕЩАЕМ.** Технически Android позволяет подменить чужой размер одноимённым своим, но библиотека объявляет публичными ровно два ресурса (проверено лично, файл `public.txt` внутри библиотеки: `yandex_ads_startup_initialization` и `yandex_ads_startup_initialization_disabled`), а все размеры крестика и счётчика — внутренние. Приём неподдерживаемый: молча сломается при обновлении библиотеки, а вмешательство в органы управления рекламой почти наверняка нарушает правила рекламной сети. Последнее — НЕ ПРОВЕРЕНО по правилам (сайт недоступен), но выигрыша всё равно нет: см. пункт 4.

**4. Единого вида у ролика всё равно не будет.** Адаптер посредника myTarget своей разметки не содержит вовсе — он передаёт показ библиотеке myTarget, значит при выигрыше её рекламы крестик и счётчик рисует уже она, а не Яндекс. Плюс сейчас в игре стоит демонстрационный блок `demo-rewarded-yandex` (`Config/DefaultEngine.ini:90`), боевых блоков нет; чем демонстрационная заглушка отличается по виду от боевого показа — НЕ ПРОВЕРЕНО. Вывод: подгонять игру под конкретный вид ролика бессмысленно, он меняется от показа к показу.

**5. Автоматическое закрытие после досмотра — НЕ ПРОВЕРЕНО.** Настройки автозакрытия в библиотеке нет (поиск по её ресурсам пуст), но закрывается ли ролик сам по завершении показа — это поведение работающего кода, из файла не видно. Проверяется только живым показом на устройстве. Прежняя моя догадка, что автозакрытие запрещено правилами сетей, так и осталась догадкой и в этой сессии подтверждения не получила.

**РЕШЕНИЕ: в коде игры не меняем ничего.** Влиять нам нечем, а единственный технический обход отвергнут как неподдерживаемый и рискованный. Что реально доступно: (а) проверить живьём на телефоне, закрывается ли ролик сам после досмотра; (б) когда появятся боевые рекламные блоки, посмотреть на них живьём — картинка может отличаться от демонстрационной; (в) если размер элементов останется больным местом, обращаться в поддержку Яндекса, а не переделывать у себя.

**Организационный урок сессии.** Выхода в интернет у команды нет ни у кого, включая помощников. Любую задачу вида «изучи документацию» либо ставим на источник, лежащий на диске, либо просим Рината прислать текст страницы.

**Дополнение ADR-068 (решение Рината 2026-08-11).** Вопрос закрыт окончательно: «Думаю лучше не трогать этот вопрос. Пусть показывается как показывается». Ничего в игре по внешнему виду рекламы не делаем, в поддержку Яндекса не пишем, к теме не возвращаемся — если только сам Ринат не поднимет её заново после боевых рекламных блоков.

## ADR-069 — ContrarySurvivor: английский язык становится отдельной задачей на потом (Ринат, 2026-08-12)

**Повод.** Задание издателя на окно «Поддержать автора» требовало английских текстов и кадра английской версии окна для приёмки. Проверка показала, что английской версии игры не существует вовсе: в упаковку попадает единственный язык (`Config/DefaultGame.ini:29`, строка `+CulturesToStage=ru`), а в папке переводов лежит только русский набор (`Content/Localization/Game/ru/` — `Game.po`, `Game.archive`, `Game.locres`; никакой другой папки языка нет). Проверено двумя способами: чтением настроек упаковки и перечислением файлов папки переводов.

**Решение Рината (дословно).** «Английский язык запланируй отдельной задачей. Займемся ей позже. Он (язык) должен будет переключаться в меню настроек. Должен быть переведен весь UI и все диалоги. Но это всё позже. Пока просто запланируй эту задачу.»

**Что это значит на практике (объём будущей задачи):**
1. Английский добавляется в упаковку вторым языком, русский остаётся исходным.
2. В меню настроек появляется переключатель языка. Сейчас такого пункта на экране настроек нет.
3. Переводится весь интерфейс и все диалоги, а не только новые окна.

**Известная ловушка, которая обязана быть решена ПЕРВОЙ (иначе перевод ломает игру).** Имена предметов и квестов сейчас служат одновременно текстом на экране и служебным ключом: прогресс квеста считается посимвольным сравнением строк (`Components/QuestComponent.cpp:204` и `252`, поля `AMasterInventoryItem::ItemName` и `FQuest::RequiredItemName` — обычные строки). При смене языка сравнение перестанет совпадать и квесты перестанут засчитываться. Разведка и разбор — `docs/contrary-survivor/loc-stage2-plan.md` (составлена `cpp-dev` 2026-07-20, 492 строки). Дублировать её сюда не нужно, она и есть источник по объёму работ.

**Что сделано сейчас, чтобы не создавать долг.** Английские строки окна «Поддержать автора» издатель прислал готовыми; они не выбрасываются, а забираются в отчёт задачи и лягут в перевод, когда до него дойдут руки. Отдельный язык в проект сейчас НЕ добавляется. Пункт приёмки издателя «кадр английской версии окна» на этой волне закрыт быть не может — это сказано издателю прямо, а не обойдено.

## ADR-070 — ContrarySurvivor: окно «Поддержать автора» сделано и отдано Ринату отдельным файлом на плоском холсте (2026-08-12)

**Что построено.** Добровольная точка показа рекламы, куда игрок приходит сам: две точки входа (пункт главного меню строго между «Настройки» и «Сообщество»; строка в меню паузы рядом с «Сообщество» и политикой), внутри окна две одинаковые кнопки — «Посмотреть рекламу» и «Другие способы поддержать». Награда за просмотр не выдаётся, порога по игровому времени у этой точки нет, ролик не готов — кнопки просмотра нет вовсе. Реклама это четвёртая точка показа (`AdUnitIdSupportAuthor`, пока пустая до боевого блока), адрес записи о поддержке — `SupportPostUrl` в кавычках. Коммиты `d2462a1` (окно и обе точки входа) и `7cbe386` (отдельный файл окна).

**Пруфы, проверенные лидом лично:** сборки `Saved/build-support-0812-b.log` и `Saved/build-supportwbp-0812-b.log` со строками линковки; прогон `Saved/tests-supportwbp-0812-final.log` — 141 тест прошёл, 0 провалено (было 133 до волны, восемь новых); состав дерева `Saved/gen-dumpslots-supportwbp-0812.log`; кадр окна из живой игры `Saved/support-frames/02-support-window.png`, просмотрен лидом.

**Решение Рината 08-12 (дословно):** «Сделай его WBP и что бы там всё легко мышкой и клавиатурой настраивалось и двигалось (без пунктирной таблицы - подложки, которая всё блокирует)».

**Что из этого следует как правило для будущих окон.** Окно, которое Ринат правит сам, строится ПЛОСКО: корневой холст и все элементы его прямыми детьми, каждый со своим положением и размером. Обёртки-контейнеры (вертикальный и горизонтальный ящик, размерная коробка) и подложки-родители запрещены: в дизайнере они дают пунктирную сетку и намертво запрещают таскать элементы мышкой. Затемнение экрана и подложка окна кладутся соседями на дно холста, а не родителями, иначе они перехватывают выделение при щелчке. Единственное допустимое вложение — подпись внутри своей кнопки (иначе спрятанная кнопка оставит надпись висеть в воздухе).

**Три следствия плоского холста, решённые сразу.** Первое: элементы на холсте не смыкаются сами, поэтому спрятанная кнопка просмотра оставила бы дыру — вторая кнопка подтягивается на её место и возвращается назад, когда ролик снова готов, причём родное место запоминается один раз и возврат кладёт кнопку туда, куда её поставит Ринат. Второе: строка благодарности в файле окна оставлена видимой, чтобы за неё можно было взяться мышкой, а прячет её теперь код при открытии окна. Третье: файл окна помечен как отданный владельцу — генератор не перезаписывает его никогда, даже принудительно, дополнять можно только режимом дополнения. Сходимость имён между файлом окна и кодом держит тест `ContrarySurvivor.SupportAuthor.DesignerAssetBindsToCode`, который перебирает поля самого класса, поэтому забыть про новый элемент нельзя.

**Дополнение к ADR-070 (коммит `e6fd856`, 144 теста прошло / 0 провалено, `Saved/tests-ownerowned-0812-final.log`).**

1. **Найден и закрыт дефект, который стирал бы ручную настройку Рината.** Код решал, можно ли красить окно, по признаку, который выставляется движком только при наличии живого игрока, а владелец применяет оформление сразу после создания окна. При расхождении в порядке окно из дизайнера перекрашивалось поверх ручных правок — в прогоне это видно дословно: цвет заголовка стал розовым, кегль с 24 прыгнул на 99, заливка кнопки стала бирюзовой. Теперь основание одно и надёжное: отметка «это дерево построили мы сами» ставится прямо внутри сборки кодового окна; не мы строили — не трогаем ничего, кроме текстов. Держит тест `OwnerEditsSurviveApplyStyle`, который снимает геометрию и цвета живого файла, применяет заведомо чужой стиль и требует, чтобы не сдвинулось ни на точку.

2. **⛔ ОПАСНЫЙ КЛЮЧ ГЕНЕРАТОРА (урок, стоил перезаписи чужого файла).** Ключ полной перезаписи у генератора окон НЕ точечный: он начинает пересоздавать ВСЕ окна подряд, а не указанное. При проверке защиты он успел перезаписать `Content/UI/WBP_TouchControls.uasset` (экранные кнопки, файл с правками Рината от 08-07) и упал на следующем окне. Файл возвращён сразу, в коммит не попал (проверено лидом: последний коммит этого файла — `1ea5e2d` от 08-07). Правило: этот ключ применять только по прямому поручению лида и только при чистом дереве, чтобы любую перезапись можно было откатить.

## ADR-071 — ContrarySurvivor: обыск кучи тел одним нажатием и заметный вид обысканного тела (задание издателя 11.08.2026, решения лида 13.08.2026)

**Откуда задача.** Живой плейтест 11.08.2026: человек со стороны отбился от стаи у логова волков, обыскал ОДНО тело из кучи в три-четыре туши и ушёл искать шкуры по локации, хотя все шкуры лежали у него под ногами. Причина не в невнимательности: обысканное и необысканное тело выглядят одинаково, и куча одинаковых туш читается как один предмет. Это первые минуты игры и первое задание, терять игрока здесь нельзя.

**Что решено сделать (задание издателя, пункты 3.1–3.4).** Одно нажатие «Обыскать» забирает содержимое всех необысканных тел в радиусе; в подсказке появляется количество вида «Обыскать (4)», при одном теле число не пишется. Обысканное тело сразу и заметно меняется на вид. После группового обыска игрок получает ОДНУ сводку о добыче, а не четыре сообщения подряд. Ящики, схроны и прочие контейнеры работают как раньше. Запрещено: подсказка-надпись «обыщи всех волков», автоматический подбор лута при смерти врага, отдельная вторая кнопка «обыскать всё».

**Развилки, которых не было в задании, — решения лида (обязательны для исполнителя).**

1. **Куда девается обыск как действие.** Одно нажатие открывает ОДНО окно обыска, в котором лежит содержимое всех тел группы вперемешку, а кнопка «Забрать всё» опустошает всю группу разом. Окно обыска не убирается и второй кнопки рядом не появляется — это прямой запрет задания, а само окно с кнопкой «Забрать всё» в игре уже есть (`UI/CorpseLootWidget.cpp:351`).

2. **Радиус группы — 600 единиц (6 метров) от того тела, которое подсветила подсказка.** Обоснование: волки стаей падают вокруг игрока в пределах пары метров, шесть метров накрывают такую кучу с запасом, а тела из соседних углов локации в него не попадают. Цепочки «от тела к телу» запрещены: они бы выгребли пол-локации за одно нажатие. Число вынесено в правимое поле, чтобы Ринат подкрутил его после живой проверки. ⚠ НЕ ПРОВЕРЕНО живым замером разлёта тел после боя у логова — проверяется на живом прогоне.

3. **Вид обысканного тела — уход в землю.** Пустое тело через 1 секунду начинает опускаться, за 2 секунды уходит на 150 единиц вниз и исчезает; все три числа правятся в редакторе. Красить тело в другой цвет запрещено: какие материалы стоят на волке и бандите — неизвестно, а красить вслепую нельзя. Уход в землю виден с одного взгляда и не требует ни надписей, ни подсказок.

4. **Сводка о добыче** показывается существующим всплывающим сообщением (`Retention/OnboardingComponent.cpp:139`) одной строкой вида «Получено: 4 шкуры волка, 12 монет». Ничего нового для этого не заводится — прямое требование задания.

5. **Переполнение рюкзака.** Вместимости у рюкзака в игре сегодня НЕТ вообще: отказ добавления возможен только при пустом предмете (`Private/UInventoryComponent.cpp:25-72`). Выдумывать вместимость запрещено — это отдельное решение по игре, а не побочная правка. Делается честная ветка поведения: не влезло — тело остаётся полным, в землю не уходит и снова попадает под следующее нажатие, игроку сказано словами. ⛔ Проверить эту ветку живьём сегодня нечем, и в отчёте это должно быть написано прямо.

**Приёмка (что требует издатель).** Кадр подсказки «Обыскать (4)» над кучей тел после боя у логова; кадр той же кучи сразу после обыска, где видно изменение тел; кадр или строка сводки о полученном; строки журнала, подтверждающие, что за одно нажатие в рюкзак попала добыча со всех тел группы; названный радиус с одной строкой обоснования.

## ADR-072 — ContrarySurvivor: подсказка про перезарядку ролика в окне «Поддержать автора» (Ринат, 13.08.2026)

**Откуда задача.** Живая проверка Рината на телефоне 13.08: после досмотра ролика кнопка «Посмотреть рекламу» пропадает (следующий ролик ещё не загружен), игрок не понимает, куда она делась и вернётся ли. Ринат: «надо как-то объяснить игроку что новая кнопка появится через 30-60 секунд и после обновления этого окна».

**Решение (вариант Б, выбор Рината после развилки).** После завершения ролика (и досмотр, и закрытие игроком), если следующий ролик ещё не готов, под текстом «Спасибо» показывается строка: «Новый ролик будет готов через несколько секунд — загляните в это окно ещё раз.» Если ролик готов сразу — строки нет. Первоначальный текст «через 30–60 секунд» исправлен по факту: журнал телефона 13.08 (phone-1313-b2.log:1233,1258) показал перезарядку ролика меньше чем за секунду.

**Границы (чтобы не разойтись с заданием издателя).** Кнопка остаётся просто скрытой — не серой и не заблокированной, дословный запрет издателя в силе. При обычном открытии окна без готового ролика подсказка НЕ показывается: задание требует «окно остаётся с одной кнопкой», шуметь там нечем. Подсказка живёт только в паре с «Спасибо» после просмотра.

**Отвергнуто.** Возврат кнопки прямо в открытом окне по событию загрузки ролика — отступление от задания издателя; делается только по отдельному решению Рината.
